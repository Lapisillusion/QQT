# 首版 AI 通信方案对比

第 36 问已选定原生 WebSocket＋自定义 JSON，每名 AI 使用一条参赛长连接承载观察、查询与决策。本文保留选型依据与其他方案比较。第 37 问已确认 UI 采用独立 WebSocket＋JSON 传输实时状态、事件与运行控制，HTTP 提供 UI 资源与回放读取；UI 与 AI 使用不同接口和连接，关闭 UI 不导致 AI 出局。已确认架构为 Windows 本机、.NET 10、ASP.NET Core，同进程同时 1 局、每局 4 名 AI。

## 选型依据

通信需要支持服务端主动下发决策开始信号与局部观察、AI 多次查询额外信息、查询响应与扣费反馈、提交计划和锁定反馈，以及淘汰和结束通知。

所有方案都必须遵守既有规则：世界在决策期间冻结，在线但未提交动作继续等待，首次有效计划锁定；查询每次成功处理都收费，包括重发，动作重发不重复执行。对局开始后，只在参赛连接明确关闭或发生连接错误时判掉线出局，不加心跳超时检测，不支持重连恢复本局资格。准备阶段同类事件只释放席位并接受新登记。

现阶段更应比较接入约定、服务端实现工作和规则兼容性，而不是假设吞吐或延迟排名。没有本项目的协议性能实测，也尚未指定未来 AI 客户端语言。

## 通信通道与游戏规则分开

WebSocket 是双向通信通道，JSON 是可选择的消息编码。SignalR 是更高层的实时通信框架，通常可以使用 WebSocket 作为底层通道，同时增加 Hub 调用、握手及消息格式等约定。HTTP＋SSE 将请求响应与服务端事件下发分开；gRPC 则通过服务定义与客户端代码表达调用和流。

公平决策、同刻结算、计划锁定、视野与扣费仍由对局协调器和模拟核心保证。使用某个通信框架不会自动得到这些游戏语义。

## 方案比较

| 方案 | 一轮中的用法 | AI 接入要求 | 服务端需要承担的工作 | 当前适用判断 |
| --- | --- | --- | --- | --- |
| 原生 WebSocket＋自定义 JSON | 一条长连接承载观察下发、查询请求／响应、计划提交／确认 | WebSocket 能力与约定 JSON 消息 | 消息分发、请求与响应关联、发送队列、连接关闭与错误通知 | 优先推荐；应用协议明确，能直接保留现有掉线语义 |
| SignalR | 服务端发送决策通知，AI 调用查询与提交等 Hub 方法 | SignalR SDK 或实现其 Hub 协议；普通 JSON WebSocket 客户端不能直接接入 | 仍须验证轮次、预算、锁定与串行裁决；还须适配超时及重连行为 | 若未来客户端接受相应 SDK，可减少部分通信封装；当前默认超时不匹配，需先验证适配 |
| HTTP＋SSE | SSE 持续下发观察与通知；HTTP 请求查询和提交计划 | HTTP 客户端、SSE 流解析与参赛会话关联 | 关联事件通道与请求身份、处理请求并发与轮次、映射参赛通道断开 | 请求响应容易独立查看，但参赛生命期分散在两种交互中 |
| gRPC＋Protobuf | 用双向流承载决策消息，或组合服务端流与查询／提交调用 | 接受服务描述、代码生成、gRPC 客户端及消息类型 | 定义服务与消息，维护生成工具，处理流生命期、关联和裁决 | 适合已有 gRPC 工具链或重视生成客户端的场景；当前尚无这类已确认需求 |

## 原生 WebSocket＋JSON

ASP.NET Core 提供原生 WebSocket 支持，通道可以持续双向收发，参见 [官方文档](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0)。本项目可以在该通道上定义观察、查询、响应、提交和确认消息。

主要代价是我们要实现应用层消息分发与关联：例如区分当前对局与轮次，将查询结果关联到对应请求，并保证每个玩家扣费与锁定按顺序处理。消息形状、大小限制和错误反馈仍需协议设计。WebSocket 本身不提供游戏请求的去重、收费或计划锁定语义。

不启用心跳超时断开即可保留当前掉线约定。官方文档说明原生 WebSocket 的 KeepAliveTimeout 默认禁用；协议层保活与按心跳超时判出局是不同事情。仍不能保证网络中断后立刻收到关闭或错误通知，这一等待可能性已在规则中确认。

一条参赛连接对应一个由服务端分配并绑定的玩家编号，请求只能操作绑定玩家。四人登记后 UI 手动开始；满员拒绝额外登记、不设候补，准备阶段席位释放后可重新申请。局末通知后关闭 AI 连接，下一局重新连接登记。AI 查询与动作携带 gameId、roundId、requestId，错局或错轮拒绝，不扣费、不锁定；requestId 不改变查询重发扣费和动作重发不重复执行的规则。AI 的观察和查询响应走参赛通道，浏览器的全局数据走独立 UI 接口；首版本机 UI 全局数据、运行控制和记录读取接口不校验凭据。

## SignalR

SignalR 提供调用与响应等通信封装，Microsoft 对多数实时 Web 应用推荐采用它，参见 [WebSocket 与 SignalR 的官方说明](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0)。因此不能仅凭“有封装”就断言它比原生 WebSocket 慢。

客户端必须接受 SignalR 的额外协议约定。其 Hub 协议包含握手与调用等消息，见 [官方 Hub 协议](https://github.com/dotnet/aspnetcore/blob/main/src/SignalR/docs/specs/HubProtocol.md)。即便使用 JSON 编码，也不能只发送本项目的普通 JSON 对象便认为已经接入 SignalR。

默认行为需要特别处理：服务端 ClientTimeoutInterval 默认为 30 秒，超过这个间隔未收到客户端消息或保活消息，会认为客户端断开；KeepAliveInterval 默认为 15 秒，见 [官方配置文档](https://learn.microsoft.com/en-us/aspnet/core/signalr/configuration?view=aspnetcore-10.0)。这与当前“不加心跳超时检测”的规则不同。若选此方案，须验证是否能在选定版本与客户端组合中保持该规则，不能直接将默认配置当作兼容。首版也不得通过重连恢复出局资格。

如果所有接入方本来就使用可接受的 SignalR SDK，其封装价值更明显；未来 AI 使用语言和已有依赖尚未指定，目前不能假定这一前提成立。

## HTTP＋SSE

SSE 是服务端到客户端的单向事件通道，因此查询和计划提交要另用 HTTP 请求，见 [SSE 文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。例如观察通过事件通道下发，付费查询使用请求响应，提交计划再发另一请求。付费查询具有扣费副作用，接口设计应避免将它当作可缓存的纯读取操作。

这种方式便于分别检查请求与响应，但需明确参赛会话由哪条持久通道维持。单次 HTTP 请求正常结束不等于 AI 掉线，也不能据此取消参赛。仍须处理多个请求的轮次校验与顺序，不能通过各 HTTP 请求并发扣费或修改计划。

如果使用浏览器 EventSource，默认的连接恢复行为也不能直接用于恢复 AI 参赛身份；本题针对 AI 接入，不要求 AI 使用 EventSource。

## gRPC＋Protobuf

gRPC 支持双向流，并通常通过 Protobuf 定义服务和消息、生成客户端代码，见 [官方核心概念](https://grpc.io/docs/what-is-grpc/core-concepts/)。这可以减少手写调用接口与消息类型的工作，代价是引入服务描述、代码生成和相应依赖。

本项目可以用分子／分母字段表达精确时间，用整数坐标表达地图位置；选 gRPC 不需要改变已有游戏规则。流结束或连接错误需要映射到参赛掉线，截止期限和自动重试也必须按现有规则审查，不能把“AI 久未决策”变成超时出局。

当前 AI 与 UI 是独立模块，因此不以浏览器能否直接使用 gRPC 作为淘汰 AI 协议方案的理由。UI 可以采用另外的通信方式。尚无性能测试证明这里需要二进制消息或 gRPC 的吞吐能力。

## 已确认选择与实施细节

已确认采用原生 WebSocket＋自定义 JSON。这是依据本项目独立 AI 接入、明确请求语义、连接关闭／报错出局且不使用心跳超时等需求作出的设计判断，不是协议性能排名。

如果未来客户端依赖和运行目标改变，可以另行重新权衡。当前 AI 方案、玩家编号与连接绑定、登记／开局／局末连接处理、请求关联与重发语义已确定，其他消息字段、大小限制和具体错误响应在实施时完善。UI 已选定独立 WebSocket＋JSON 的实时展示与控制、HTTP 的资源与回放读取。现阶段优先跑通验证程序，一般协议细节不作为前置问答；涉及核心机制、公平性或范围的新歧义再确认。
