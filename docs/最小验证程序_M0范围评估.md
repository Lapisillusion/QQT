# 最小验证程序 M0：范围评估与建议

日期：2026-10-13。本文针对用户提出的第一个可运行场景做裁剪，不替代 [完整首版规则](首版模拟规则_已确认版.md) 和 [开发详细设计](程序开发详细设计_第一版.md)。M0 已按该范围实现并验收，实际结果见 [实施与验收记录](M0实施与验收记录.md)。

用户提出：脚本驱动四个玩家，走到各自出生点旁边一格，放泡泡，再走到安全点；Server 模拟移动、放置、爆炸移除和箱子销毁；UI 展示过程。安全点已明确为同一出生点的另一个向内相邻格。

## 1. 评估结论

这个起步合理，能以一个短场景跑通“脚本输入 → 服务端模拟 → 网络输出 → 浏览器展示”。不需要先完成真实 AI 决策器接入或所有比赛功能。

建议把当前交付称为 M0 场景验证，完整首版仍保留道具、局部观察、信息查询、正式 AI 接入与回放等已确认要求。先验证这条流程，不把一个正向场景当作全部规则已经完成。

## 2. 初始地图已经确定

正式地形采用固定规则生成，不随机生成墙或箱子：

- 内部 21×21，UI 外圈硬墙另画，不进入逻辑坐标。
- 人读行列编号同时为偶数时为硬墙；零基坐标对应 x、y 同时为奇数。
- 四角各预留出生格和两个向内相邻格为空地，共 12 格。
- 其他非硬墙格全部为箱子；初始 100 硬墙、329 箱子。

完整对局随机分配玩家四角，并按配置数量随机预藏箱内道具；地形本身固定。算法可以直接按格子坐标生成，不需要地图编辑器。M0 建议使用固定四角角色绑定作为验证输入，不生成道具，以便重复检查相同结果；这是场景裁剪，不更改完整首版的随机出生与道具规则。

## 3. 四人镜像脚本

使用已确认初始值：1 格/tick、泡泡寿命 3 tick、每方向范围 1。脚本使用四组预设动作，不开发四个 AI 客户端。

| 玩家角色 | 出生点 | 放置点 | 返回出生点 | 安全点 |
| --- | --- | --- | --- | --- |
| 左上 | A1 | B1 | A1 | A2 |
| 右上 | U1 | T1 | U1 | U2 |
| 左下 | A21 | B21 | A21 | A20 |
| 右下 | U21 | T21 | U21 | U20 |

第一轮选择到达相邻格中心时放置，不在出生点放。路径必须经出生格转弯，不能直接斜走到安全点。

| 逻辑时间 | 四人对称执行 | 预期结果 |
| --- | --- | --- |
| t=0 | 初始化在四角，开始第 1 轮 | 4 人、0 泡泡、329 箱子 |
| 第 1 轮，0→1 | 向水平内侧移动一格，终点放置一颗 | t=1 放置成功，共 4 颗，分别预定 t=4 引爆 |
| 第 2 轮，1→2 | 反向回到各自出生点 | 可以从刚放的泡泡格离开 |
| 第 3 轮，2→3 | 向竖直内侧移动一格 | 到达 A2、U2、A20、U20，均在爆炸覆盖外 |
| 第 4 轮，3→4 | 原地等待 | t=4 四颗引爆并移除，破坏四个箱子，四人安全 |

爆炸破坏的箱子为 C1、S1、C21、S21；B2、T2、B20、T20 均为硬墙，阻断相应方向。以左上为例，B1 爆炸只覆盖 B1、A1、C1；A2 不在覆盖内。

这个场景四人相距很远，没有泡泡连锁或多人冲突。它不能证明这些功能已经实现。

## 4. 必须补上的最少功能

| 必须项 | 原因 | 最小实现 |
| --- | --- | --- |
| 世界初始化与恢复 | 没有固定输入，无法重复验证 | 建立地图、四人和初始属性；重新开始恢复箱子、玩家和计时 |
| 四方向移动及阻挡检查 | 路径需要回出生点后转弯 | 每轮一格，检查边界、墙、箱子、目的格泡泡；当前泡泡格允许离开 |
| 统一逻辑 tick 和实际放置计时 | 否则泡泡可能在角色逃离前后错误引爆 | 终点 t=1 放置，到期为 1+3=4；不用浏览器或独立现实计时器计寿命 |
| 爆炸覆盖和地形传播 | 箱子销毁需要正确的覆盖集合 | 十字范围 1，硬墙不覆盖且停止，箱子覆盖并销毁后停止 |
| 最小安全校验 | 只看画面走到某处不能证明“安全” | Server 在爆炸时检查覆盖是否包含玩家所在格，输出受击结果；本场景预期四人都未受击 |
| 场景完成与结果检查 | 四人都存活，不会自然产生竞技胜负 | 显式执行 4 轮后检查结果，显示“验证通过／失败”，停在最终画面 |
| 可观察的服务端输出 | UI 需要知道何时移动、放置和销毁 | 完整状态、移动段与带逻辑时刻的事件；UI 只绘制服务端确认结果 |

安全校验不要求本阶段实现完整淘汰与胜负系统。若脚本实际路径偏离预期或出现受击，判场景验证失败并保留画面，不伪造比赛胜负。

四轮是脚本明确指定的验证终点；结束后不申请第五轮动作，不将正常场景完成误判成“脚本耗尽”。若在指定四轮之内缺少某人的必要动作，则仍是脚本错误／验证未完成，不能用自动等待掩盖。

## 5. 建议暂缓的功能

- 真实 AI WebSocket、参赛登记、掉线、重发处理、决策等待和查询预算。
- 局部视野、付费信息和 AI 详细分析。
- 道具、随机出生、连锁、同格叠放、复杂泡泡通行例外。
- 完整受击淘汰、竞技胜负、500 tick 上限。
- 通用脚本语言、脚本选择器、复杂配置界面。
- JSONL 持久化、回放、故障恢复流程和性能压测。
- UI 的暂停／单步、回放时间轴、积压追赶和精细美术。

M0 先用单一固定脚本、内存事件日志和一次“开始／重新运行”入口。原详细设计的完整记录、暂停和回放等仍是后续首版要求；这份清单建议将其从首次可运行交付中暂缓，不永久删除。

本场景到期和中心到达均在整数边界，因此可以先按整 tick 驱动这个受限场景，同时保存服务端移动段供 UI 插值。不需要先完成任意移速、任意分数寿命与全部途中事件调度；也不能据此把完整模型改成无途中判定的瞬间跨格。

## 6. 最少的模块与通信

| 模块 | M0 职责 |
| --- | --- |
| `ScenarioRunner` | 初始化，按轮提供四人预设计划，控制四轮运行与完成检查 |
| `GameSimulation` | 接收本轮计划，执行移动、放置、到期、覆盖、箱子销毁和安全校验 |
| `UiEndpoint` | 接收开始／重跑命令，推送状态与事件；重复启动不能同时创建两个运行 |
| 浏览器页面 | Canvas 绘制地图、四人、泡泡与爆炸，显示 tick、计数、日志和验证结果 |

这四个职责先以少量类实现，不先完成全部详细设计模块。仍由一个 ASP.NET Core 进程提供前端资源和 UI WebSocket，浏览器代码独立运行。

服务端建议按已确认的每 tick 约 1 秒节奏提供过程，首轮可以立即开始；UI 根据服务端段记录播放移动，爆炸动画不持续伤害。暂不实现完整积压处理。一个脚本内存日志足够查看本次结果，不要求先搭建记录系统。

## 7. 验证通过的客观条件

按用户补充的测试规范，M0 以实际运行四人模拟脚本，并通过日志核对关键结果作为最终验收目标；不要求先建立单元测试项目，不编写低价值或重复验证实现细节的用例。以下条件是本次脚本的验收结果，不要求每条各写一个测试。

四轮结束时必须同时满足：

- 四名玩家分别位于 A2、U2、A20、U20，且爆炸安全检查均为未受击。
- 恰好在 t=1 创建四颗泡泡，预定 t=4；四颗在 t=4 爆炸，最终泡泡数为 0。
- 只有 C1、S1、C21、S21 四个箱子被毁，箱子总数从 329 变为 325。
- 硬墙仍为 100 格，其他箱子保持原状，初始预留空地未被改变为阻挡。
- UI 的位置、泡泡、箱子与最终计数一致；日志可查到四次放置、四次爆炸和四次箱子销毁。
- 重新运行得到相同逻辑结果。

只有在安全检查存在疑问或需要回归实际错误时，再增加一个小型负向检查：让一个玩家第 3 轮留在出生格，则 t=4 应报告受击，场景验证失败。它能区分安全检查始终返回“安全”的错误，不要求新增竞技玩法、UI 控件或批量测试；不作为默认新增测试任务。

M0 完成只表示上述受限流程已验证，不代表真实 AI 接入、道具、途中事件、连锁或完整对战已完成。
