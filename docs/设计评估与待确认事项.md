# 泡泡堂 AI 对战平台设计评估

当前已确认规则汇总见 [首版模拟规则_已确认版](首版模拟规则_已确认版.md)。本文保留方案比较与技术建议，演示参数不作为正式默认值。

本文针对 `初稿.docx` 中的模拟方式、表现改善、可行性与技术选型问题提出方案，并纳入用户后续确认。目标已经确定为用于 AI 比拼的简化规则游戏；当前阶段先实现服务端，不实现 AI 算法客户端。用户已选择格子地图加移动进度、服务端附带浏览器观战 UI，以及同步决策。技术组合已确认普通 C# 模拟核心、单个 ASP.NET Core 服务端兼任 AI 接口与 UI 后端，以及原生 TypeScript＋Canvas 2D＋HTML/CSS 浏览器前端；AI 和 UI 独立采用 WebSocket＋JSON，HTTP 提供 UI 资源与回放。一般协议与运行细节在实施时完善，不逐项询问。具体设计见 [首版系统架构设计](系统架构设计_首版.md)。

受限 M0 已实现并通过功能验收，见 M0实施与验收记录.md；仍无性能压测结果。本文的比较结果是功能、规则复杂度和开发适配性的判断，不是跑分结果。首版每局人数已定 4 人，先本机运行服务端与浏览器 UI、在本机验证 AI 接口；首版每个服务端进程同时 1 局，可连续运行多局；首版以 Windows 本机运行与验收，训练需求暂定，不据此承诺吞吐、延迟或工期。

## 初稿已经明确的需求

- 以泡泡堂为背景，提供 AI 算法之间的对战环境。
- Server 负责模拟与裁决，AI Client 根据收到的数据提交决策，通过网络交换信息。
- 决策期间可能需要向 Server 查询更多数据。
- 需要可视化观察对战，不使用游戏引擎，希望方案轻量。
- 作者偏向格子化方案，但希望改善表现，并评估可行性与技术选型。

## 后续已经确认的范围

- 做简化规则的 AI 对战游戏，具体规则共同确认，不以复现原作作为验收目标。
- 当前先实现服务端；AI 客户端暂不实现。
- 服务端已选定 C#＋ASP.NET Core、.NET 10 LTS；下文保留与其他方案的比较作为选型依据。
- 移动模型选择 B：跨格具有实际耗时，服务端记录匀速移动进度并执行途中判定；采用只在格子中心开始下一段移动的简化方向。
- 首版仍包含服务端附带的浏览器观战 UI，不实现 AI 算法客户端。AI 客户端是独立决策器，接收观察、请求额外可用信息并上报 tick 决策，不参与 UI；服务端负责模拟并通过附带 UI 展示过程，两个交互流程相互独立。UI 展示服务端掌握的完整游戏信息，用于观察游戏和评估 AI，不受 AI 的局部视野与付费查询展示限制；AI 仍按自己的信息规则决策。
- 原型内部逻辑地图完整 21×21，尺寸不含外圈墙；UI 额外绘制硬墙边框。逻辑越界按阻挡处理，爆炸和视野裁剪到内部地图，不把可视外圈计作可操作格。
- 四名玩家每局随机分配到内部地图四个角格中心，服务端保存种子用于复现。每角初始仅预留出生格和两个向内相邻格为空地，共 3 格，不放墙或箱子，其余格子按固定布局决定。
- 首版固定初始地图为 21×21：行、列序号同时为偶数的交点是硬墙，如 B2、D2、B4、D4，直到 T20；其余除四角 12 格预留空地外全为箱子。共 100 墙、329 箱子、12 空地，已生成 [首版地图布局](地图布局_21x21_首版.md)，每局恢复此布局。
- 采用同步决策，优先保证 AI 获得相同的决策机会。
- 所有玩家初始属性统一：速度 1 格/tick、容量上限 3 颗、每方向爆炸范围 1 格、寿命 3 tick、视野 R=2、每轮行动值 10 点。可调参数最终通过配置文件提供，在场泡泡数和剩余行动值随各自操作独立变化。
- 首版速度限定整数格/tick，统一初始值为 1 格/tick，可由移速道具提升，下一轮生效，本轮计划与旧轮终点结算使用旧属性。每轮首次有效移动与放置计划提交后锁定，不允许替换，本轮不再接受该玩家查询；动作重发只确认原计划，不重复执行。
- 未判掉线的玩家未提交有效动作时继续等待，整局逻辑时间保持冻结，不因迟交默认等待动作或自动淘汰。只在连接明确关闭或发生连接错误时判掉线，不加心跳超时检测，不支持重连恢复。等待时在当前逻辑时刻处理出局并检查胜负；模拟时在下一个内部结算点先推进位置，取消掉线者未执行计划，再结算爆炸，合并掉线与受击淘汰后检查胜负，结束则不再放置或移动。已放泡泡按淘汰者规则保留。网络中断但服务端尚未收到关闭或错误通知时，仍可能继续等待。全部剩余存活玩家提交有效计划才共同推进；已提交者保持锁定，不因其他玩家迟交获得新的查询或修改机会。
- 轮初固定本轮移动方向和计划距离，不允许途中主动改向或停止；允许整轮原地等待。在中心检查下一格，遇到阻挡就停在当前中心并终止本轮剩余移动；阻挡稍后消失也不自动重启。未到达位置的放置请求不执行。
- 泡泡阻挡新发起的进入。生成时已经在该格的所有玩家均可离开，离开后不能重新进入；已开始的一格移动允许完成，即使目标格途中新放泡泡，到达后也可离开。离开许可针对具体泡泡，不表示该格永久可通行。
- 同格允许多颗泡泡，已有泡泡不使新放置请求仅因占格失败。容量按所属玩家同时在场的泡泡颗数计算，不按占用格数计算；同格一颗引爆会立即连锁其余泡泡，每颗各自贡献范围并释放所属玩家容量。每个玩家每轮在每个中心最多请求一颗。
- 放置失败只影响当次请求，移动与后续放置照常执行，并反馈失败原因。同刻先统一放置，再检查下一格阻挡并启动新移动段；已提前开始的移动段保留完成许可。
- 时间模型已重新选择为匀速移动、允许对应途中时刻引爆；每颗按实际放置时刻加固定寿命计时，不推迟到大 tick 或固定小步边界。内部使用分数 tick 准确比较和结算，AI 按统一决策周期同步决策；对外时间采用分子、分母整数对象，例如 {"numerator":1,"denominator":3} 表示 1/3 tick，整数 3 tick 表示为 {"numerator":3,"denominator":1}。
- 逻辑时间单位已确认 1 tick＝1 个抽象逻辑单位，支持途中时刻。首版优先实时观战，由服务端按可配置最小 tick 推进间隔运行，收齐有效计划且间隔已到才推进，不等待 UI 完播回执。最小推进间隔初始为 1 秒，可配置，按相邻两轮实际开始模拟的现实时间计时；首轮收齐计划且允许运行即可开始。现实间隔不改变逻辑规则，AI 未提交仍继续等待，实际间隔可以更长。
- 协议位置用从 0 开始的整数对 (x,y)，各为 0～20，x 向右、y 向下；界面仍显示 A～U、1～21。A1=(0,0)，B2=(1,1)，协议硬墙为 x、y 同时为奇数，保持人读行列同时为偶数的地图规则。
- 泡泡固定寿命初始值为 3 个逻辑 tick，L=3T。未获得移速增益的初始速度一格、中心放置的正常到期在 tick 边界，但这不撤销途中引爆能力；不使用现实决策等待时间计算寿命。
- 同刻主要顺序已确认：先形成该时刻玩家位置 → 处理待处理掉线、取消计划 → 按爆炸前同一地图计算到期与连锁 → 统一清理、合并掉线与受击淘汰 → 立即检查胜负，结束则停止 → 中心批量拾取（增益下一轮生效） → 统一新放置 → 检查阻挡并启动新移动段。恰好到达安全格可避开爆炸，新发起的移动不能改变引爆时刻位置；旧轮终点事件完成后，激活增益再生成新轮观察。
- 爆炸传播已确认：硬墙格不覆盖且阻断；箱子格覆盖、销毁并阻断；遇到另一格泡泡触发连锁，原射线继续按剩余范围传播。同刻全部到期与连锁使用爆炸前同一地图计算，统一移除箱子和已爆炸泡泡。
- 下一轮观察在旧轮终点的爆炸、淘汰和终点放置全部完成后生成；冻结快照再收集下一轮动作。下一轮从同一逻辑时刻开始，已经结算的事件不重复执行。
- AI 采用局部视野：以角色中心所属格为中心，横纵距离各不超过 R 的方形区域，裁剪到地图边界；初始 R=2，最大 5×5，墙、箱子不遮挡。地形和实体只显示视野内，视野外未知。固定地图 21×21、每局 4 人、四角随机分配和保存种子已定。
- 免费泡泡观察提供视野内位置和本轮局部查询编号；编号本轮固定、下轮重新分配。行动值只用于信息查询，移动和放置不消耗，每轮恢复固定额度、不累积。所有泡泡详情统一收费，包括自己的泡泡；每次成功查询都扣费，包括重复查询和网络重发，失败不扣费且不返回详情。
- 自身玩家状态免费：位置、速度、容量上限、当前在场泡泡数、剩余行动值等自身游戏状态；自身泡泡详情不属于免费例外。视野内其他玩家免费提供位置和跨轮稳定玩家编号，详情付费返回身份（即该稳定编号）、速度、泡泡容量上限和当前在场泡泡数，不返回其剩余行动值。初始单价：每颗泡泡详情 1 点，每位其他玩家详情 2 点。
- 首版初始每局 4 人自由混战。每批同刻到期、连锁和淘汰全部结算后立即检查：剩一人获胜，零人平局，立即停止模拟、不执行后续放置或移动。淘汰者已放泡泡保留，只有对局继续才推进计时。最大 tick 初始上限 500，最后终点先结算爆炸和淘汰；若仍多人，再完成旧计划终点放置并判平，不开第 501 轮。
- 爆炸采用瞬时伤害：只在引爆时刻检查玩家中心所在格是否属于危险区，属于则淘汰；爆炸后不保留持续伤害。移动进度小于一半算起点格，达到一半算目标格。
- 基础玩法已确认：四方向移动；玩家互不阻挡且允许同格；四方向爆炸及连锁；不可破坏墙与可破坏箱子；受击直接淘汰；首期包含移速 +1 格/tick、同时在场泡泡容量 +1 颗、每方向爆炸范围 +1 格三种道具；不包含困泡救援和复活。
- 首版主要玩法、移动与放置语义及初始参数已确认，以 [首版模拟规则](首版模拟规则_已确认版.md) 为准；其余一般协议字段与实现细节在实施时完善，仅影响玩法、公平性或范围的重要选择继续确认。

配置错误处理已确认：创建新局时读不到配置、JSON 格式错误或参数不合法，拒绝创建并在 UI 显示具体原因，修正后重试，不回退到默认值或上一份有效配置。

## 已确认选择对应的服务端流程

地图仍然是格子。角色额外记录起点、终点、移动进度与总耗时，模拟核心按内部事件时刻推进位置并执行判定。移动耗时不等同于 AI 决策等待时间，也不等同于浏览器动画时长。

同步决策按以下流程组织：

1. 完成旧轮终点爆炸、淘汰、拾取与终点放置后，统一激活待生效道具增益，再固定一份状态版本，为各参与者生成对应局部观察。所有观察对应同一逻辑时刻；方形视野初始 R=2，墙和箱子不遮挡。地形和实体只显示视野内，免费泡泡信息为位置和轮内编号；字段编码仍待协议确定。
2. 收集这一决策轮的动作。逻辑时间冻结，移动与泡泡计时不推进；玩家可在首次有效提交前查询。首次有效提交即锁定并关闭该玩家本轮查询，重发只确认原计划、不重复执行。未判掉线的玩家未提交则继续等待，不因迟交补动作或淘汰；只在连接明确关闭或发生连接错误时判掉线，不加心跳超时检测，不支持重连。等待期间在当前逻辑时刻处理掉线出局并检查胜负；对局继续时通知剩余玩家掉线编号并禁用该玩家查询，查询失败不扣费，保留原观察、已查询结果、剩余行动值和已锁定计划，不重开决策轮；未提交者继续查询和提交。已放泡泡仍保留。具体等待提示在实施时完善。
3. 将本轮动作作为一个批次交给模拟核心，避免网络先到的动作先修改游戏状态。
4. 推进本轮逻辑时间，逐一处理期间的到期爆炸、连锁和其他已获准事件。先把所有玩家推进到事件时刻，再按同刻主要顺序裁决；全部爆炸使用同一份爆炸前地图，不能由连接遍历顺序决定。
5. 为 UI 提供带逻辑时刻的全局状态与模拟事件，展示服务端掌握的完整游戏信息；独立为 AI 生成下一轮局部观察，开始下一轮决策。

同步收集与内部模拟时间精度分开。用 decisionRound 表示决策轮次，并为事件记录实际逻辑时间，避免把内部事件当作新的决策轮。推荐按事件时刻分段推进，具体实现仍需结合时间表示确定；内部推进不额外增加 AI 的观察或决策机会。

本轮方向和计划距离在轮初确定，不允许途中主动改向或停止，允许整轮等待；阻挡截停是例外。本轮沿途放置位置可预先选择，只有实际到达对应中心且存活才尝试放置。等待一段时间后再启动移动、途中新增指令或跨轮保留旧计划均不作为已确认能力。放置失败只影响当次请求已确认，完整动作协议与反馈字段仍待定；演示速度、容量和寿命不作为正式参数。

速度已经限定为整数格/tick，当前首版统一初始值为 1 格/tick，可由移速道具提升，下一轮生效，本轮计划与旧轮终点结算使用旧属性。未遇阻且存活时，按本轮已生效整数速度完整移动相应格数，在中心结束；遇阻也在中心截停。下一轮可在中心重新选择方向。首次有效提交锁定、动作重发不重复执行与查询重发成功再次扣费是两种独立规则。

动作计划包含非法方向或放置位置不在所选方向的计划路径上时，整份拒绝并返回原因，不执行任何子部分、不锁定本轮，允许玩家修正后重交。合法方向遇阻依旧截停，执行时容量不足依旧只失败当次放置请求；不将这些执行结果作为整份计划无效的依据。

浏览器只显示服务器确认的状态与事件。特别是同步等待期间，画面不能自行把角色推到服务器尚未到达的位置，也不能按现实时间提前引爆泡泡。可以在已确认状态之间播放动画，但播放结束仍未收到新的推进结果时，应停在最后确认位置，并展示等待状态。

首版浏览器 UI 的必要目标是展示完整地图、所有玩家位置与状态、所有泡泡位置与详情，以及移动、放置、爆炸、淘汰和对局结果等信息，方便用户观察游戏进行和评估各个 AI。UI 展示不受 AI 局部视野与付费查询限制，与 AI 决策器独立；AI 通过自己的协议收发局部观察、查询和决策，不通过 UI 操作。首版加入暂停／继续和按 tick 单步控制服务端模拟：暂停在 tick 边界生效，单步仍须收齐所有存活玩家的有效计划，推进最多一个 tick 后暂停，途中判出胜负则立即结束。保存对局记录并支持 UI 回放已确认；回放提供播放／暂停、前后逐 tick 查看与按 tick 时间轴跳转，只控制记录展示，不修改真实对局或请求 AI 新动作。正常动画与回放 1 倍速基准初始为 1 秒／逻辑 tick、独立配置已确认；首版回放固定 1 倍，不提供倍速选择；记录存于服务端本地目录，每局一个 JSONL 文件，进行中追加保存、结束保留。游戏数值配置用 JSON，每局创建时读取并固定，文件修改只影响新局，实际配置写入记录。具体布局与记录字段待设计；记录写入失败停止进一步 tick 推进、UI 报错并保留现场与已写记录，不因此改判竞技胜负。首版不恢复故障后的未结束对局，由人工终止并标未完成，修复后新开，不判竞技输赢；未完成记录可回放已保存的完整有效前缀，明确标未完成，不补模拟或推断缺失胜负。

UI 内容范围进一步确认：首版只展示全局游戏状态与事件日志，不加入选中 AI 的详细分析面板。AI 详细观察、查询与扣费、决策和执行记录仍保存，详细分析通过对局记录查看；单个 AI 分析面板不属于首版待实现需求。

不实现 AI 算法客户端期间，首版已确认通过预设脚本驱动验证，指定各玩家每轮查询与动作，经过服务端同一套扣费、校验、锁定与模拟规则，UI 展示并保存记录；该工具不包含策略算法，手动逐轮输入入口不列为首版必做。已确认在 UI 选择预设脚本、可选指定种子并手动创建／开始对局，结束后保留结果、手动开始下一局。脚本已确认为 JSON，按轮组织有序请求，创建时加载并校验结构，具体字段待设计；AI 接入已选定原生 WebSocket＋JSON。

## 高速移动与瞬时爆炸判定

用户已确认实际放置时刻加固定寿命，并允许在对应途中时刻引爆。服务端在实际引爆时刻判定位置，不因玩家在本轮曾经过危险格就判定受击。爆炸后的显示动画不形成持续伤害。此前较大 tick 或固定小步边界的引爆限制已由本次决定替代。

详细流程与两种时间模型的比较已修订，见 [高速移动与事件时间模型](高速移动与事件时间模型.md)。

### 爆炸时刻的位置

在每个引爆逻辑时刻，先依据实际位置与移动进度得到玩家中心所在格，再判断是否属于该批爆炸覆盖。不到半程算起点格，达到半程算目标格。

玩家在引爆前已经离开该格，或引爆后才进入该格，都不受这次爆炸影响。一个 tick 多格时，遍历本 tick 经过格子只用于处理阻挡和移动衔接，不能把所有经过格都当作引爆瞬间占用的格子。

每个决策轮必须逐一处理内部到期时刻和连锁，不能跳到轮次终点才检查。每颗泡泡预定到期为实际放置时刻加固定寿命，实际引爆可能因连锁提前；相邻泡泡不保证按预定到期先后分别爆炸。

### 速度和阻挡

建议位置或进度使用明确的细分单位，速度表示为每单位逻辑时间的移动量。按匀速运动推进到下一事件时刻，同时扫描经过路径，保证不会穿墙或穿过约定阻挡。速度优势还取决于正式速度范围和放置规则，本次时间选择不自动限制速度。

内部时间采用精确分数 tick，对外时间采用分子、分母整数对象。首版统一初始速度 1 格/tick，坐标用从 0 开始的整数对，已确认数值见规则汇总。泡泡阻挡、离开许可、已开始移动段完成和中心遇阻终止本轮已定。首期三种道具的类型与属性增量已确认；生成按配置数量开局预藏箱子、中心拾取、同刻到达者都获得、下一轮生效且持续至局末无上限、已放泡泡使用实际爆炸轮已生效范围等已确认，其他协议字段在实施时完善；最小 tick 推进间隔初始 1 秒、从上一轮实际开始模拟计时已确认。

### 同刻结算顺序

沿用已确认的主要顺序：先把移动推进到事件时刻，再统一结算到期泡泡与连锁，按该时刻位置判定淘汰，最后执行存活玩家该时刻的新动作。若恰好到中心并打算放置，同时有旧泡泡到期，先爆炸和淘汰，再允许存活者放置。

新增胜负检查已确认：该批全部同刻连锁和淘汰完成后，先统一检查剩余人数。剩一获胜、零人平局，立即结束，不再执行同刻后续放置或下一移动段，也不等待本 tick 末。不能在同批连锁尚未完成时提前选出获胜者。淘汰者已放泡泡继续存在；若场上仍多人，对局继续推进它们的计时和连锁。

传播和销毁快照已确认：硬墙不覆盖并阻断；箱子覆盖、销毁并阻断；泡泡触发连锁但不截断原射线。该时刻全部到期与连锁按爆炸开始前的地图计算，随后统一移除箱子与泡泡，不因先销毁箱子使另一条同刻射线穿透。每批统一淘汰后立即检查胜负，结束则不执行后续动作。

## 已确认玩法与动作

受击方式、基础玩法、轮内固定方向、阻挡截停、泡泡阻挡例外、同格叠放与连锁、每中心一颗请求、放置失败独立处理、先放置再启动新移动段、爆炸传播和销毁快照、初始数值与胜负机制均已确认。具体协议字段在实施时完善。

### 途中受击

用户已确认按角色中心所在格受击：引爆时进度小于一半算起点格，达到一半算目标格。只检查引爆瞬间是否被覆盖，不处理身体边缘，也不保留持续伤害。引爆与淘汰先于该边界新动作的顺序已确认。

“角色中心所在格”与“角色到达格子中心”不同：前者在途中也可以计算，后者表示角色已经到达该格的中心位置。后续动作协议与 UI 文案需要区分这两个概念。

### 基础玩法

用户已接受基础包：四方向移动；玩家互不阻挡且允许同格；泡泡向四方向爆炸并允许连锁；地图包含不可破坏墙与可破坏箱子；受击直接淘汰；首期包含移速 +1 格/tick、同时在场泡泡容量 +1 颗、每方向爆炸范围 +1 格三种道具；不包含困泡救援或复活。

这个基础包用于控制首版规则范围。容量 3 颗、寿命 3 tick、每方向范围 1 格、21×21 地图、四人自由混战、即时胜负与 500 tick 上限均已另行确认；爆炸伤害瞬时，动画播放时长初始 1 秒/tick。数值依据用户逐项确认，不由基础包自行推导。

### 移动动作

每轮提交一个移动方向或整轮等待。选择方向时，计划距离按该轮速度确定；例如三格/T 计划直线移动三格。途中不接受主动改向或停止；死亡取消后续移动，墙、箱子和泡泡阻挡属于截停例外，因此终点不保证总在三格外。

已确认完成已经开始的一格移动，即使目标格途中新放泡泡也不立即截停，到达后允许离开。在格子中心开始下一段前检查阻挡，发现阻挡则停在当前中心并终止本轮剩余移动；障碍稍后消失也不自动恢复。

### 放泡泡的触发与位置

轮初可以预选本轮路径上的中心作为放置位置，包括起点；只有实际到达该中心且存活才尝试放置。例如 A1→D1 可选 A1、B1、C1、D1，先前“不在 A1 放置”只是特定例子的选择，不是禁止在起点放置。

泡泡容量限制每个玩家同时在场的颗数，不等于可选位置数，也不按泡泡占用格数计算。已确认同格允许多颗，多个玩家同刻放置不因竞争该格而失败；每次仍需检查自身容量和其他已确认的合法条件。放置失败只失败当次请求，不取消移动和后续放置，并反馈失败原因。

已确认每个玩家每轮在每个中心最多请求一颗。叠放可以来自不同玩家或不同轮次，不允许用同一轮重复中心请求来一次放多颗。同格一颗爆炸会立即连锁其余泡泡，每颗按自己的范围产生覆盖，并分别释放所属玩家的容量。硬墙、箱子阻断各自射线，其他泡泡触发连锁但原射线继续传播。多颗泡泡分别记录归属、实际放置时刻、固定寿命和范围，不合并成共享计时的泡泡。

泡泡已经确定阻挡新发起的进入。生成时已经在格内的所有玩家均可离开，已经开始向该格移动的玩家可完成该段并离开；离开后不得重新进入仍存在的该泡泡格。离开许可随玩家离开或泡泡消失失效，不扩展到以后新生成的泡泡。

### 同轮移动与放置

轮初提交移动与沿途放置计划，服务端根据中心实际到达时刻执行放置。起点请求在轮初尝试，其他请求在到达相应中心时尝试；同刻旧泡泡先爆炸和判定淘汰，存活玩家再执行新放置。

同刻全部新放置统一处理完毕，再检查下一格阻挡并开始新的移动段。例如甲到 B1，乙同刻在 C1 放置，甲不能在该时刻新启动 B1→C1，而应在 B1 终止本轮移动；若甲早已开始该段，则仍可完成。新泡泡的离开许可适用于该时刻同格玩家和此前已开始进入该格的玩家。

阻挡或淘汰后未到达位置的请求不能远程生效。已确认本轮遇阻在当前中心截停，终止剩余移动，未到达位置的请求不执行；障碍消失也不自动恢复。截停中心本身若是已选放置点且玩家存活，仍按正常放置条件尝试，这不属于未到达位置。旧轮末到达中心的请求不得在下一轮重复执行；错局、错轮拒绝与动作重发不重复执行已确认，其他反馈字段在实施时完善。

## 对两个原始方案的判断

地图使用格子，与角色只能瞬间跨格，并不是同一个设计决定。格子可以用于定义墙、泡泡和爆炸范围；角色同时可以拥有格内位置或跨格移动进度。

同样，采用每秒 60 个模拟步不会自动还原原作。碰撞形状、转向、速度、放泡泡时机、受击和爆炸结算规则才决定玩法是否相似。没有指定版本和实测资料，不能声称某一方案具有原作精度。

| 方案 | 服务端状态 | 表现与判定 | 主要代价 |
| --- | --- | --- | --- |
| 精细坐标模拟 | 角色精细位置与碰撞形状，地图仍可格子化 | 可表达更细的移动和接触判定；还原程度取决于规则 | 转向、贴墙和碰撞处理更复杂 |
| 离散跨格 | 每次结算直接改变角色所在格 | 适合离散策略环境；画面可平滑，但途中没有真实判定 | 对时序和空间的简化较多 |
| 格子地图加移动进度 | 起点、终点、耗时、当前进度，或整数细分坐标 | 可平滑移动，并在途中执行选定的碰撞和受击规则 | 需明确途中占位、转向和受击规则 |

**历史比较建议：** 如果目标是简化规则的 AI 对战，同时希望移动有时间过程，可优先评估第三种方案。如果目标只是离散策略比拼，第二种方案也可以成立，不必额外引入细粒度移动。首版已选择第三种，不重新开放选型。

## 两种格子移动方式的详细比较

下文 A 为直接跨格，B 为服务端记录跨格进度。两者都采用格子地图，都能设计为确定性模拟，也都可以使用同步或实时决策。移动模型与对局调度是两个独立选择。

| 比较项 | A 直接跨格 | B 记录移动进度 |
| --- | --- | --- |
| 核心状态 | 所在格与必要的移动冷却 | 起点格、终点格、移动进度与耗时 |
| 速度表示 | 每次推进允许移动的格数，或移动冷却规则 | 每格所需模拟步数，或明确的整数细分速度 |
| 途中受击 | 没有格间位置，按离散位置和结算顺序裁决 | 可在移动过程中裁决，但必须定义途中如何受击 |
| 转向与停止 | 在允许提交移动的时刻改变目标 | 需要决定只能到格子中心改变方向，还是允许途中改变 |
| AI 状态与搜索 | 状态更少，搜索不必表达格间进度；仍需要考虑爆炸时间 | 除格子与时间外，可能需要考虑移动进度与尚未完成的动作 |
| 多人冲突 | 同格、换位等仍需明确定义 | 还可能涉及对向移动、途中相遇和目的格占用 |
| 画面 | 动画位置可能暂时与服务器所在格不同 | 画面可以根据服务端进度呈现位置 |
| 测试重点 | 同时动作、冷却、路径经过格与结算顺序 | A 的问题，加上途中受击、完成边界和动作衔接 |
| 性能影响 | 每次推进检查允许的离散移动 | 每步更新活动移动并执行相应判定；增量成本需要实测 |
| 适合的目标 | 优先做规则清晰、实现较快的离散策略平台 | 希望移动时间和躲避时机也成为比赛的一部分 |

两者不是仅有视觉差异。例如在从一个格子移向相邻格的过程中发生爆炸，A 只能按当时的离散位置处理；B 可以根据进度和明确的受击规则处理。给 A 加动画不会产生 B 的判定能力。

**用户已选择 B 的简化方向。** 保留相邻格之间的移动时间，只在格子中心开始下一段移动；受击按中心所在格判定，玩家互不阻挡。这样可让到达时机成为策略因素，同时把任意几何转向与贴墙行为留在首版范围之外。整轮方向锁定、按预选中心放置、整轮等待和阻挡截停等规则已确认。

选择 A 同样合理：如果更看重格子搜索和快速完成首版，它的规则规模更小。应明确将其作为离散玩法，而不要通过动画暗示服务器执行了途中判定。首版建议选定一种模型，先验证玩法与裁决，不同时维护两套规则。

## 改善方案 2 的具体方法

### 分开空间、逻辑时间、决策和画面

1. 地图单位用于表达空间，例如格子坐标。
2. 模拟逻辑时间用于推进移动、泡泡计时和受击，途中事件按其对应时刻处理。
3. AI 决策周期用于收集动作，一次决策可以覆盖多个内部事件。
4. 观战画面按浏览器刷新节奏绘制，不决定服务端结果。

模拟与渲染分离的背景资料可参见 [Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/)。本次选择允许对应途中时刻引爆，不能以该文为依据将爆炸重新限制在固定步边界。

逻辑周期为一个抽象 tick，内部事件按精确分数时间结算。每轮方向与计划距离在首次有效提交时锁定，途中不主动撤销、改向或停止；遇阻终止本轮移动。每个动作可覆盖多个内部事件，不增加 AI 决策机会。

### 服务端记录移动过程

一种候选表示为：起点格、终点格、开始逻辑时刻、速度或总耗时、当前进度。按事件时刻推进并裁决；AI 观察中提供必要进度信息，让 AI 能预测自己的实际位置。

若要支持半途停止、反向或自由转向，可以改用整数细分坐标。整数表示有利于定义明确的舍入规则，但不会单独保证确定性；仍需固定随机数、更新顺序和全部裁决规则。

用户已确认以半程为界决定引爆时的受击所在格，不采用身体几何重叠判定。高速移动仍需检查经过的阻挡，爆炸只在引爆边界按该时刻位置判定。

### 观战端做插值

观战端按服务器 tick 对齐状态，在相邻已知位置之间插值。泡泡出现、爆炸、死亡等离散事件按照事件时刻切换，不能把这些事件也当作位置进行插值。使用网络快照插值通常会引入缓冲延迟；缓冲大小需根据网络与观战要求确定。

只做插值可以改善视觉，但无法恢复服务器没有模拟的途中碰撞和受击。

## Server Client 架构补充

建议分成三个职责，初版可以在一个服务内实现，不必立即拆成多个服务：

- **模拟核心：** 输入当前状态和已裁决动作，产生下一状态与事件。这里不直接读取网络、浏览器帧率或墙上时间。
- **对局控制：** 管理连接、发放观察、收集动作、处理掉线与非法动作，把最终有效动作交给模拟核心；在线迟交继续等待，不增加动作或心跳超时淘汰。
- **观战界面：** 展示完整状态和事件，提供已确认的暂停／继续与按 tick 单步控制；暂停在 tick 边界生效，单步须收齐有效计划，途中判出胜负则立即结束。提供记录回放，支持播放／暂停、前后逐 tick 查看与按 tick 时间轴跳转，回放操作不修改真实对局或请求 AI 新动作。

逻辑时间用于移动与泡泡计时；现实时间用于协调器安排最小 tick 推进间隔，两者分开。首版优先实时观战，收齐有效计划且间隔已到才推进，不依赖 UI 完播回执；不设置动作迟交超时淘汰。回放读取记录，不根据当前播放速度重新裁决。

### 决策与查询

建议每份观察关联对局、决策轮次、逻辑时刻和快照标识。已确认先完成旧轮终点事件再生成观察，下一轮动作从同一时刻开始，已完成事件不重复执行。AI 查询与动作请求均携带 gameId、roundId、requestId；对局或轮次不匹配时拒绝，不扣费、不锁定计划。requestId 用于关联响应，不改变查询重发成功仍扣费与动作重发不重复执行的规则。具体标识类型与反馈字段待协议设计。对局开始后首版不支持重连恢复本局参赛资格，掉线即出局。

格子坐标的 JSON 格式已确认采用 {"x":0,"y":0} 对象，仍为从 0 开始的整数坐标，x 向右、y 向下。动作中的放置计划使用格子坐标对象列表，由服务端校验是否属于计划路径并按实际到达中心执行；不采用沿途格数列表。重复项及越界坐标等校验边界在实施时完善，涉及玩法语义的新歧义再确认。

真实 AI 登记流程已确认：服务端分配玩家编号并绑定连接，本局跨轮稳定，后续请求只能操作绑定玩家。四名 AI 均完成登记后由 UI 手动开始并统一下发首轮观察，不足四人保持准备。准备阶段连接明确关闭或报错时释放席位，允许新连接登记；此时不按开局后的规则判出局。脚本验证仍由 UI 手动创建／开始。席位已满时明确拒绝额外登记并返回原因，不设候补队列，已有席位释放后可重新申请。局末通知后关闭 AI 参赛连接，下一局重新连接、登记并分配编号。具体登记消息在实施时完善。

首版本机 UI 全局数据、运行控制与对局记录接口不校验访问凭据；UI 与 AI 仍分别使用独立接口和连接。

局部视野已确认：以玩家中心所属格 (cx,cy) 为中心，格 (x,y) 满足 |x-cx|≤R 且 |y-cy|≤R 即属于方形视野，再裁剪地图边界。初始 R=2，原型地图尺寸 21×21，硬墙和箱子不遮挡。地形和实体均只显示视野内，视野外未知。免费泡泡观察提供位置和本轮编号，归属、范围和预定到期不免费下发；不能通过基础观察默认公开视野外实体或其他玩家全部状态。

观察只发送视野内格子的坐标与地形，以及视野内实体列表，不发送完整地图矩阵。未发送格子视为本轮未知，不代表空地；客户端可以自行保留历史记忆，服务器不将视野外历史信息作为本轮最新状态下发。

初稿中的“查询更多数据”需要明确查询内容。如果是在同一次决策中补充观察，建议查询同一个冻结快照，并使用相同的可见信息权限。否则客户端可能通过反复查询看到后续变化，导致不同 AI 的信息不一致。查询次数、消息大小及是否计入决策预算需要确认。

可优先把确定需要的信息随观察一次下发，减少网络往返；是否保留额外查询接口由实际需求决定。

### 行动值与信息查询

已确认每轮有固定行动值，额度每轮重置，未用部分不累积；仅额外信息查询消耗，移动和放置不消耗。免费观察给视野内泡泡位置，客户端选择需要了解的泡泡，按颗一次付费获得归属、范围和准确预定到期，再提交本轮移动及放置计划。预定到期仍可能因连锁提前，不是保证的实际引爆时间。

查询发生在收集本轮动作的冻结阶段，读取该轮同一快照，不推进逻辑时间、不改变泡泡寿命，也不开放途中改向或停止。执行计划后不能把查询变成对正在模拟状态的实时观察。自身剩余行动值随已处理查询更新并免费反馈，属于决策预算变化，不表示游戏时间推进。收费目标和条件由服务端验证，响应应能关联本轮快照；具体协议待定。

每轮行动值初始额度 10 点，初始单价为每颗泡泡详情 1 点、每位其他玩家详情 2 点，均已确认。当前对象为视野内已看到的泡泡；扩展视野或查询视野外实体不作为已确认能力。每颗免费提供位置和本轮局部查询编号，编号在当前快照内固定，下一轮重新分配，不是跨轮稳定身份；同格多颗也有不同编号。

每次成功查询都扣费，重复查询同一泡泡不豁免；服务端即使复用缓存响应，也应按该规则计费。额度不足、目标不在本轮可查列表或请求过期时失败，不扣行动值、不返回详情，现实决策时间仍照常计算。请求应引用正确的对局、轮次和快照，避免下轮编号复用误查其他泡泡；具体字段格式待协议确认。

已确认同一 requestId 查询网络重发不免除收费：每次收到且成功处理都扣费，不能按 requestId 去重来避免再次收费。额度不足等失败仍不扣费，也不返回详情。动作提交则首次有效计划锁定，重发只确认原计划，不重复执行；提交后不再接受该玩家本轮查询，迟到查询不会成功处理或扣费。

自身玩家状态全部免费，至少包括位置、速度、容量上限、当前在场泡泡数和剩余行动值；自身在场数量可能因视野外自有泡泡爆炸而变化，这是已确认的自身状态信息。所有泡泡详情查询统一收费，包括自己的泡泡；客户端仍可根据反馈、记忆及公开规则推断。

视野内其他玩家免费提供位置和跨轮稳定玩家编号，不使用泡泡的轮内局部编号。按人付费查询返回身份、速度、泡泡容量上限、当前在场泡泡数四项，不返回其剩余行动值；结果读取该轮冻结快照。身份就是该稳定编号，实际新增状态为速度、容量上限、在场数量。每位详情初始单价 2 点行动值，自身玩家状态免费。

稳定编号仅便于跨轮识别，不授权读取视野外玩家的当前位置或详情；目标仍需在本轮可查视野列表中。当前在场泡泡数可能包含该玩家位于查询者视野外的泡泡，这属于已确认的付费状态字段；不会因此返回那些泡泡的位置或详情。

信息购买控制的是服务端额外披露，客户端仍可记忆并推断。例如自己成功放置的泡泡若已知放置时刻和固定寿命，可自行推算预定到期；若某参数全局统一公开，也能自行得知，不能把这种推断当作未付费违规。正式字段和规则公开范围需使查询具有实际价值。

### 对战调度与公平性

有两种候选方式：

- **同步决策（已选）：** 给各 AI 发出同一逻辑时刻的观察，等待所有存活参与者首次有效提交后共同推进。未提交则整局继续等待；现实播放速度会受等待影响，逻辑时间和最大 tick 时限不受现实等待时间影响。
- **实时决策：** 模拟持续推进，动作按预先定义的时间窗口生效。适合强调持续实时反应；网络延迟和动作归属更复杂。

首版已确认 Windows 本机运行与验收，每进程同时 1 局、可连续运行多局；决策耗时统计和相同资源约束仍待确认。未提交继续等待、首个有效动作锁定已经确认。首版已确认保存对局记录并支持 UI 回放，记录初始配置与地图、随机种子、各 AI 的观察／查询／决策、模拟事件和掉线出局的逻辑时刻；查询处理结果与扣费情况需保留。回放读取记录，不重新向 AI 请求决策或根据回放时的网络到达顺序生成比赛结果，支持播放／暂停、前后逐 tick 查看和按 tick 时间轴跳转。建议记录规则版本，以便后续规则调整时识别旧记录；回放 1 倍速基准初始 1 秒／逻辑 tick 已确认；首版回放固定 1 倍，记录采用本地每局独立 JSONL 文件、进行中逐条追加；具体字段与目录待设计；写入失败暂停进一步推进并保留现场，首版不恢复故障后的未结束对局，由人工终止并标未完成，修复后新开，不判竞技输赢；未完成记录可回放已保存的完整有效前缀，明确标未完成，不补模拟或推断缺失胜负。

同一 tick 的移动、放泡泡、到期爆炸、连锁爆炸、障碍销毁与受击需要明确结算规则。例如“到达安全格”与“爆炸发生”同 tick 时谁先成立，会直接改变结果，不能靠程序循环顺序偶然决定。

## 技术选型与备选比较

### 可视化

浏览器采用已确认的原生 TypeScript＋Canvas 2D＋HTML/CSS，符合“不用游戏引擎”的首版目标。Canvas 原生支持二维绘制，参见 [MDN Canvas API](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API)。地图与角色可以画在 Canvas 上，连接状态和控制按钮使用 HTML。

绘制使用 [requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)。它跟随屏幕刷新，后台标签页通常会暂停回调，因此服务端不能依赖它推进模拟。

用户已确认首版采用服务端附带的浏览器观战界面，以及暂停／继续、按 tick 单步和记录回放等基础控件。原生 TypeScript＋Canvas 2D＋HTML/CSS 已选定；具体展示布局仍待设计，尚无包大小或渲染性能实测结论。

### 首版服务端与 UI 的承载关系（已确认）

已确认在一个 ASP.NET Core 服务端进程内承载游戏模拟、AI 接口与 UI 后端。游戏规则和精确分数时间运算放在独立的普通 C# 模拟核心中；ASP.NET Core 负责连接与请求处理、服务端运行控制、全局状态与事件输出、回放记录读取，以及浏览器页面资源的提供。ASP.NET Core 可以直接提供 HTML、CSS 与 JavaScript 等静态资源，参见 [官方静态资源文档](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/static-files?view=aspnetcore-10.0)。首版本机、单进程同时一局的范围下，暂没有已确认需求要求将 UI 后端与模拟拆为独立服务。

浏览器执行前端代码并绘制画面。已确认用 Canvas 2D 绘制地图、角色、泡泡与爆炸，用 HTML/CSS 展示状态、日志、控制按钮与回放时间轴，用 TypeScript 组织前端逻辑并编译为浏览器执行的 JavaScript。浏览器负责展示已确认模拟过程及发送运行控制请求；碰撞、放置、爆炸、容量与胜负仍由 C# 模拟核心结算，页面刷新频率不决定游戏 tick。

浏览器是前端的运行环境，Canvas 2D 是绘图 API；Vue、React 等页面框架属于另外的代码组织选择，并非采用浏览器 UI 后必须使用的组件。首版已选定原生 TypeScript＋Canvas 2D＋HTML/CSS，不引入 Vue／React 页面框架。若未来 UI 规模改变，可另行评估页面框架，不影响独立的 C# 模拟核心与现有职责划分。

AI 决策器通过自己的协议获取局部观察、请求付费信息并提交动作；浏览器 UI 独立接收服务端全局状态、模拟事件与回放数据。二者可以连接同一个服务端，但数据内容和交互职责分开。AI 接入已确认为原生 WebSocket＋JSON，每名 AI 一条参赛长连接承载观察、查询和决策；UI 已确认为独立 WebSocket＋JSON 的实时展示与运行控制，HTTP 提供页面资源与回放读取；AI 和 UI 使用不同接口与连接。

### 通信

AI 已选定原生 WebSocket＋JSON，观察、查询与决策通过每名 AI 的参赛长连接交换；UI 已选择独立 WebSocket＋JSON 传输实时全局状态、事件与运行控制，HTTP 提供资源与回放；关闭 UI 不导致 AI 出局。具体协议版本、字段类型和消息验证还需设计。标准 WebSocket 的浏览器 API 不提供自动背压，需控制观战快照发送频率与队列长度，参见 [MDN WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)。

已确认实时 UI 出现播放积压时追赶最新完整全局状态并跳过积压动画，不暂停服务端；运行控制仍作用于当前服务端对局。完整事件日志与对局记录保留，不能因跳过展示而丢弃 AI 查询、动作或裁决记录，细节可回放查看。正常动画与回放 1 倍速基准初始 1 秒／逻辑 tick、与服务端推进间隔独立配置已确认；积压只计已模拟完成且尚未开始播放的轮，当前播放轮不计，不按消息或事件数计数；达到 2 轮时触发，阈值可配置。

### 服务端

| 候选 | 对本项目的优势 | 成本与需要验证的地方 | 当前比较结论 |
| --- | --- | --- | --- |
| C# 加 ASP.NET Core | 符合用户偏好；可以分别表达模拟核心、后台调度和网络服务；框架已有 WebSocket 支持 | 确定性、分配与回收、序列化和同局请求调度仍需设计和测量 | 已选定为首版路线 |
| Go 加 net/http | goroutine 和 channel 适合连接与对局任务的并发组织 | 用户需接受另一种服务端语言；WebSocket 库需另行选择；并发模型不自动消除比赛状态竞争 | 可作为偏好 Go 或部署方式时的备选，无现有证据要求替换 C# |
| Python 加 FastAPI | 原型迭代直观，WebSocket 支持可用；若后续算法工具使用 Python，生态衔接方便 | CPU 密集模拟不能仅依赖异步；进程间分配对局可能增加复杂度 | 算法客户端暂不做，Python 的算法生态优势不构成首版服务端的决定性理由 |
| TypeScript 加 Node.js | 网络事件处理与 JSON 数据适配直接；若后续采用浏览器 UI，可共享部分类型定义 | 长时间模拟不能阻塞网络事件循环；CPU 工作可以使用 worker，但会增加任务通信设计 | 若团队更偏好 TypeScript 可选，当前不足以抵消用户的 C# 偏好 |

FastAPI 原生提供 [WebSocket 接口](https://fastapi.tiangolo.com/advanced/websockets/)，但 [异步并发与 CPU 并行不同](https://fastapi.tiangolo.com/async/)，不能把 async 当作模拟吞吐保证。Node.js 同样需要避免 [阻塞事件循环](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)。Go 的 [goroutine 官方说明](https://go.dev/doc/faq#goroutines)支持评估其并发模型，不能证明它在本项目上的性能排名。

Node.js 的 [worker_threads 官方文档](https://nodejs.org/api/worker_threads.html)说明了 CPU 密集工作的线程方案。上述文档证明实现机制存在，不证明各语言在本游戏中的吞吐排名。也没有依据给四种方案赋予数值评分、性能倍数或开发天数。

**已确认 C# 加 ASP.NET Core，采用 .NET 10 LTS，目标框架 net10.0。** [.NET 官方支持策略](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)列明 .NET 10 为 LTS。当前本机 `dotnet --info` 显示 SDK 10.0.103 与 ASP.NET Core 10.0.3 已安装，开发环境具备相应基础；首版运行系统已确认为 Windows，本机已有 SDK 不表示其补丁版本是最新版本。

模拟核心使用普通 C# 代码表达状态与规则，不依赖 ASP.NET Core；网络与运行调度在外围实现。这样测试可以直接推进模拟，无须先建立网络连接。AI 客户端暂不实现，但未来可通过统一协议使用其他语言，服务端使用 C# 不要求算法也使用 C#。

### C# 内部实现方式比较

| 方式 | 优势 | 代价 | 建议 |
| --- | --- | --- | --- |
| 控制台或 Worker Service 承载模拟 | 适合无界面推进、动作文件输入和核心验证 | 还需补充网络入口才能成为原稿的网络服务端 | 首版采用脚本驱动验证，由 UI 选择脚本、可选指定种子并手动开始，加载细节待确认；完整服务由 ASP.NET Core 承载 |
| ASP.NET Core 承载模拟与 API | HTTP 管理接口、长连接和运行生命周期可放在同一应用内 | 需要确保请求处理不会并发修改同一局状态 | 已确认为首版完整服务端的承载方式 |
| 首版拆成网关与独立模拟进程 | 可隔离负载并分别扩展 | 需要进程通信、对局路由和故障恢复；首版已确定本机同时 1 局 | 首版采用单进程；后续有扩展需求时另行评估 |

候选组织方式为：每局状态由一个串行执行流程修改，请求处理仅提交命令；不同局在资源允许时分别调度。单局内部不要依赖多个网络回调同时改状态来获得并行。是否使用后台任务、队列以及具体容量，属于后续实现设计。

ASP.NET Core 的 [BackgroundService](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0)可以承载长期运行任务；[System.Threading.Channels](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels)可以表达生产者与消费者队列。二者不提供游戏确定性或硬实时保证。逻辑 tick 由模拟推进决定，计时器只用于按现实时间安排运行，不把一次计时器回调直接等同为精确经过一个 tick。

### 原生 WebSocket 与 SignalR 比较

针对当前同步决策、查询收费、无心跳超时与掉线出局规则的完整选型比较，见 [AI 通信方案对比](AI通信方案对比.md)。该文同时比较 HTTP＋SSE 与 gRPC；第 36 问已选定原生 WebSocket＋JSON，UI 已选择独立 WebSocket＋JSON 的实时展示与控制、HTTP 的资源与回放读取。

ASP.NET Core 两种方式均可用。Microsoft 的 [WebSocket 文档](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0)建议多数应用使用 SignalR，以获得更高层通信能力；这里需结合未来 AI 接入方式评估。

| 方案 | 得到的能力 | 本项目需要承担的工作 |
| --- | --- | --- |
| 原生 WebSocket 加自定义 JSON 消息 | 可以自行定义观察、动作和事件协议；未来客户端只需实现约定消息与 WebSocket | 消息分发、连接生命周期、请求响应关联及掉线通知需要自行实现；首版不支持重连恢复 |
| SignalR | 框架提供 Hub 调用、连接管理和分组广播等能力 | 客户端需要支持 SignalR Hub 协议或采用相应 SDK，不能直接按普通 JSON WebSocket 客户端接入 |
| HTTP 手动推进接口 | 方便在没有 AI 客户端时直接提交动作并查看结果 | 不等同于完成实时推送与 AI 调度；保留为备选，首版验证已选择预设脚本 |

SignalR 的能力与协议参见 [官方概览](https://learn.microsoft.com/en-us/aspnet/core/signalr/introduction?view=aspnetcore-10.0)。不同算法语言接入且采用简短显式协议时，原生 WebSocket 便于自定义协议；如果接入方都接受对应 SDK，SignalR 可减少通信层工作。第 36 问已选定原生 WebSocket＋自定义 JSON；连接绑定、登记与开局流程、局末关闭、对局／轮次／请求关联和重发语义均已确认，其他消息字段在实施时完善。UI 的独立 WebSocket＋JSON 实时通道与 HTTP 资源／回放读取已确认。

### 当前阶段如何验证服务端

已确认：对局未结束但本轮脚本执行完仍缺存活玩家有效计划时，结束本次验证、标记脚本错误／未完成，保留现场与记录，不判竞技输赢，修正后新开一局。此规则仅适用于验证工具，正式 AI 在线未提交仍继续等待。

## 可行性与验证边界

从功能组成看，格子规则、网络决策和二维观战都有可用的实现方式，因此架构可行。首版已确定每进程同时 1 局、每局 4 人；实际性能容量、AI 决策延迟、开发工期或训练加速倍数尚未实测。

负载至少由对局数、每局人数、地图尺寸、泡泡与连锁规模、模拟频率、决策频率、消息大小和 AI 耗时决定。应在这些目标确认后，用最小原型测量每步耗时分布、每秒推进步数、网络流量和内存，再定性能方案。

规则确认后，建议以以下场景验收：

- 高速移动跨多格不穿墙；按各引爆边界真实位置判定；爆炸后经过原覆盖格不受该次爆炸影响。
- 同 tick 到达与爆炸、同时放泡泡、连锁爆炸与障碍销毁。
- 两名角色争夺同格、交换位置和角色穿越，按确认规则裁决。
- 在线迟交保持等待，连接明确关闭／报错按阶段处理，重复动作不重复执行，过期查询及非法动作按已确认规则拒绝。
- 同初始状态、配置、种子和有效动作在核心验证中得到一致结果；UI 回放读取保存过程，不重新模拟或请求 AI。改 UI 刷新率不改变对局结果。
- 实时播放与加速运行在相同有效动作序列下产生一致逻辑结果。
