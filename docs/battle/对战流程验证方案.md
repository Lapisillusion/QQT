# 对战流程验证方案

2026-10-17 讨论后确认，2026-10-18 按本方案完成实施和验收。本文保留执行前约定的输入与独立预期；实际结果、统一入口与证据见 [运行与验收记录](对战运行与验收记录.md)。协议依据见 [逐项确认记录](对战协议_逐项确认.md)，总体范围见 [实施计划](对战流程实施计划.md)。

## 1. 验证组成与数据边界

采用一个真实 Server 进程、按本局配置启动的 2／3／4 个脚本 Client 进程，以及验证运行器。

- Client 通过正式 `/ws/ai` 登记、收观察、发送查询与计划、核对响应；只执行预设脚本，不根据场景产生策略。
- 运行器通过正式 UI 控制通道创建／开始、点击 tick，并接收全局展示数据。浏览器另行检查真实按钮和动画，运行器不代替浏览器验收。
- 运行器可以读取全局记录作断言，Client 不能借此读取隐藏状态决定行动。输入计划、查询和断线时机均来自预设脚本。
- 用预设屏障协调“已收到观察”“某请求已回复”“N−1 人已锁定”等事件，不用随机 sleep 决定请求先后。验证无推进／无新观察时使用有界现实观察窗口，同时检查服务端阶段、消息计数和逻辑现场；该窗口不是游戏超时规则。
- 泡泡目标可按脚本中预设位置解析到本轮 queryId；这只是绑定观察中的协议编号，不是策略决策。也可固定断言编号，确保同格多颗不混淆。

配置、地图、种子、编号到出生点的预期映射、逐条请求／响应预期及最终现场在执行前写入脚本，不用服务端本次实际结果生成预期。时间按精确分数核对，不以显示小数判等。

## 2. 正式地图主场景：四人完整对局

采用正式地图、默认属性、无道具、固定种子。随机出生规则仍生效，预期分配固定写入脚本；下表按西北／东北／西南／东南四角角色描述，再根据预先核对的种子映射填写实际 playerId。西南角色为预期胜者。

| 轮次／逻辑时刻 | 预设动作与关键预期 |
| --- | --- |
| 第 1 轮，0→1 | 西北到 B1、东北到 T1、西南到 B21、东南到 T21，四人均在终点放置；t=1 共 4 颗，dueAt 均为 4 |
| 第 2 轮，1→2 | 四人查询各自可见泡泡、查询一位视野外玩家，再重复查询同泡泡；余额依次为 10→9→6→5，核对泡泡归属／范围／dueAt 及玩家七项详情；随后退回各自出生格 |
| 第 3 轮，2→3 | 西北到 A2、东北到 U2、西南到 A20、东南到 U20，不放置 |
| 第 4 轮，3→4 | 四人等待；t=4 四颗爆炸，C1／S1／C21／S21 被毁，四人安全 |
| 第 5 轮，4→5 | 西北／东北／东南回出生格；西南留在 A20 |
| 第 6 轮，5→6 | 西北到 B1、东北到 T1、东南到 T21；西南仍在 A20 |
| 第 7 轮，6→7 | 西北／东北／东南在当前格放置并等待，实际 placedAt=6、dueAt=9；西南不放置 |
| 第 8～9 轮，7→9 | 四人等待；t=9 三人自爆，西南角色在 A20 获胜，不生成第 10 轮观察 |

主场景最终独立预期：硬墙 100、箱子 325、在场泡泡 0、总放置 7、总爆炸 7、毁箱 4、死亡 3、存活 1，结束时刻 9/1。死者最终位置为 B1、T1、T21；胜者位置 A20。不是“脚本耗尽所以结束”，必须实际收到竞技终局。

同一脚本分别运行自动与逐帧模式。自动无需演示点击；逐帧首轮及每轮均等待点击，未点击时不发新观察。两次除现实等待和 UI 控制记录外，观察、查询响应、锁定计划、逻辑事件与最终现场均一致；按 playerId、roundId 和脚本步骤关联对比，不要求互不相关的跨玩家网络请求以相同现实顺序到达。

## 3. 信息与锁定场景：三人固定测试环境

使用现有 initial 测试环境机制，空地图上 P1=(1,1)、P2=(2,1)、P3=(10,10)，P1 视野半径 2。预期 P2 在 visible.players，P3 在 participantIds；列表不重复、不含 P1。此场景明确为测试环境，不改变正式地图与随机出生规则。

配置 P2 speed=2、bubbleCapacity=4、blastRange=3、视野半径=3（visionWidth=7），另有一颗位于 (12,12) 的 P2 初始泡泡，使 P1 查得 activeBubbleCount=1，且不能获取该泡泡的位置或详情。P1 在 (1,1) 有一颗自有可见初始泡泡。两颗均 placedAt=0、dueAt=3，寿命 3。

P1 在首轮依次执行：

| 输入 | 预期 |
| --- | --- |
| 查询 P2 | 成功扣 2，剩余 8；七项值逐项匹配，位置 (2,1)，在场数 1 |
| 查询 P3 | 成功扣 3，剩余 5；返回包含 (10,10) 的完整七项详情 |
| 查询自身可见泡泡 | 成功扣 1，剩余 4；ownerId=P1、blastRange=1、dueAt=3/1 |
| 使用相同 requestId 重复查询该泡泡 | 再扣 1，剩余 3，不按 requestId 免费去重 |
| 再查 P3 | 扣 3，剩余 0 |
| 查询 P2、非法泡泡编号、错误 gameId／roundId | 分别失败，cost=0、data=null、余额保持 0，错误原因可区分 |
| 非法方向、重复坐标或名义路径外放置后提交合法 wait+[] | 非法整份拒绝且不锁定；合法提交锁定，返回原计划 |
| 锁定后查询、重发原计划、提交另一份计划 | 查询拒绝；动作均确认原 wait+[]，不改变或重复执行 |

免费观察断言同时检查未出现付费字段、视野外格子／泡泡、箱内道具内容，以及查询回复未额外带他人行动值。玩家返回七项字段不能只是检查字段存在，必须核对上表中特意不同的数值。

P2 提交 wait+[]，P3 保持在线不提交。在超过正常最小推进间隔的验证观察窗口内，Time=0、未执行任何动作，两颗泡泡 dueAt 仍为 3；P3 最后提交后只推进一轮，所有人位置不变，Time=1。自动模式下一轮额度应恢复到 10；逐帧模式直到下一次点击才开启新轮并恢复额度。

完成断言后，按脚本先关闭 P2、再关闭 P3 的参赛连接，预期均在当前逻辑时刻 1/1 淘汰，P1 在 (1,1) 获胜，仍保留两颗初始泡泡，未发生爆炸；必须先观察到对应处理结果再继续。自动模式保留新轮缺计划，逐帧模式保持等待按钮，均不应额外模拟。故意断线是脚本输入，与验收失败后的清理分开。

## 4. 生命周期与必要边界

使用最少预设小脚本／参数化场景，复用上述请求及断言工具，不为每个协议字段建立独立测试。

| 输入 | 核对结果 |
| --- | --- |
| N=2、3、4，分别不足员开局、满员后额外登记 | 不足不能开始；达到 N 仅就绪；额外登记拒绝；不存在假玩家／假死亡 |
| 配置非法人数；准备掉线后补位 | 非法配置拒绝创建；准备掉线仅释放席位，补足 N 后可手动开始 |
| 固定种子重复建局 | 预期出生映射一致，位置互不重复；记录保存配置、种子及实际分配 |
| 逐帧开始但不点击，随后一次点击与重复／旧轮点击 | 首轮观察受门槛约束；一次只开启一轮，不积攒许可，旧轮命令不启动下一轮 |
| 等待按钮时掉线；决策阶段查询／锁定后他人掉线 | 当前时刻淘汰，不等待点击；保留其余观察、预算与锁定；仍多人保持相应阶段，剩一人直接终局 |
| 掉线目标查询和已淘汰者遗留泡泡查询 | 玩家目标禁用、不收费；原视野内遗留泡泡仍按本轮编号与冻结详情查询 |
| 同格多个泡泡、跨轮复用 queryId | 同格泡泡编号独立，查询对应详情；旧 roundId 请求拒绝，即使该编号在新轮存在 |
| 提交几何合法但执行受阻／容量不足的计划 | 接受并锁定；实际按核心规则截停或跳过放置，不把执行失败当提交失败 |
| UI 关闭／重连；终局清理后再开下一局 | UI 关闭不淘汰玩家；手动模式可重连继续，自动可运行；终局清理不改判，新局不受旧命令或旧锁定影响 |
| 多人等待满 500 tick | 依既定终点顺序判平，不生成第 501 轮；不拿脚本容量上限代替竞技上限 |

模拟期间断线到淘汰的网络流程做实际验证；“指定内部时刻恰好收到掉线并与爆炸合并”的先后判定，使用确定性命令注入的协调器／核心检查。保留同一实际结算代码，不开放新的 AI 协议，不依赖调短 sleep 碰运气。至少覆盖：掉线未执行放置取消、遗留泡泡保留、同刻爆炸完成后再判胜负。只在上述脚本不能可靠区分错误时增加此类最少必要检查。

## 5. 成功标准与证据

- 客户端记录实际收到的观察、请求关联及回复；运行器逐条比较独立 expected，包括应缺失的字段、计费、锁定和轮次。
- 对关键时刻核对全局现场和事件，含精确放置／爆炸／死亡时间、位置、箱子与泡泡计数、最终胜者。UI 全局帧与服务端记录交叉检查，但两者一致本身不能替代独立预期。
- 真实浏览器验证至少展示正式主场景的自动和逐帧各一次，并核对按钮显示／禁用、等待阶段、实际人数、动画终点和结果。其他人数至少核对实际玩家展示；不把 WebSocket 自动化当浏览器画面已验收。
- 核心人数与事件入口改变后回归现有四人精确时间、道具及必要 M0 脚本，确保时间与同刻规则没有变化；不扩大到本次未实现的功能。
- 保存输入脚本、配置／种子、客户端消息、服务端分类日志／JSONL、运行器逐条差异和必要 UI 截图。输出区分“验证通过／失败”与“竞技获胜／平局／未完成”。
- 任意断言不符或验证等待超时即标记本次验收失败，保留现场与首个差异；先固定验证停止／未完成状态再清理连接，不因清理制造竞技结果。服务端自身故障、脚本耗尽与正常 match.ended 分开记录。

## 6. 实施与运行顺序

先实现最小真实联机路径，以 2 Client 跑通登记、观察、提交和一轮推进；再完成三人信息／锁定场景；随后运行正式四人完整对局的两种模式，补齐生命周期及必要内部事件检查，最后做核心回归与浏览器验收。

登记、淘汰与终局消息的字段及错误码已在 [协议记录](对战协议_逐项确认.md) 中按简单实现补齐，未改变本文可验收行为及范围。

场景输入放 `scripts/battle/`，运行器命令脚本放 `scripts/verification/`，记录输出放项目 artifacts 下的本次运行目录；入口为 `scripts/verification/verify-battle.ps1`，返回明确退出码，报告每个场景首个差异。500轮上限场景单独使用预设1ms最小模拟开始间隔，其余网络与浏览器场景沿用1000ms；未修改竞技逻辑时间或500轮上限。
