# 对战流程实施计划

更新日期：2026-10-18。本文保留已确认的实施计划；现已按计划完成，对应运行入口和实际证据见 [实施与验收记录](对战运行与验收记录.md)。规则依据为 [已确认规则](../首版模拟规则_已确认版.md)，工程职责参考 [详细设计](../程序开发详细设计_第一版.md)。

## 1. 本次确认与范围

- 每局人数由配置指定为 2、3 或 4，默认沿用 4；达到配置人数后就绪，由 UI 手动开局，不因满员自动开始。
- 出生点沿用正式地图四角，从中随机选取与人数相同的互不重复位置并分配；保存种子及实际分配。少于四人不生成额外玩家，地图、箱子及四角预留空地不变。
- 准备阶段参赛连接关闭／报错仍释放席位，允许补位。开局后不补位、不恢复参赛资格；等待按钮、暂停、收集决策和模拟期间掉线均淘汰。
- 掉线仍以服务端收到连接明确关闭或连接错误为依据，不新增心跳／迟交超时。UI 断开不构成参赛玩家掉线。
- 增加每局固定的“是否逐帧推进游戏”配置，默认关闭。开启时，UI 增加“tick演示”按钮，每次有效点击开启一轮决策并模拟最多一个逻辑 tick；关闭时按原设计自动推进。
- 脚本客户端仅执行预设请求，通过真实 WebSocket 连接验证观察、查询计费、提交锁定、同步推进及胜负，不实现逻辑 AI。
- 本次包含必要 UI 控制、结构化日志、每局 JSONL 记录和自动核对工具；完整回放界面及独立暂停／继续控制后续完成，不改变其首版最终范围。

## 2. 两种推进模式

### 自动模式

达到配置人数 → UI 手动开始 → 建立首轮冻结状态并下发观察 → 查询／提交 → 收齐所有存活玩家有效计划且满足最小模拟间隔 → 模拟至轮末或终局 → 未结束则开启下一轮。

### 逐帧模式

达到配置人数 → UI 手动开始 → 等待“tick演示” → 点击后建立本轮冻结状态并下发观察 → 查询／提交 → 收齐所有存活玩家有效计划且满足最小模拟间隔 → 模拟至轮末或终局 → 未结束则再次等待“tick演示”。

- 首轮也必须等点击；点击同时许可本轮决策与模拟，收齐后不再点击一次。
- 等待按钮时新轮未开启，不提前生成／下发观察，不恢复新轮预算，不接受下一轮查询或提交；位置、泡泡计时和 tick 均不增长。待生效增益在点击开启新轮时统一激活。
- 一次点击最多启动一轮，收集／模拟期间重复点击不积攒后续许可。服务端校验当前对局、待开启轮和阶段，多 UI 同时点击也只生效一次。
- 只有等待按钮且可开启下一轮时按钮启用；已结束／终止时禁用。自动模式隐藏该按钮。
- “帧”是逻辑 tick，不是浏览器绘制帧或内部结算事件；最小模拟开始间隔与动画时长仍独立配置，不依赖动画完播回执。
- 等待按钮时掉线在当前逻辑时刻淘汰并检查胜负，不消耗点击、不推进逻辑时间；仍多人则继续等待，剩一人或零人直接终局。模拟期间在下一个内部结算点处理掉线，保留既定同刻爆炸优先于最终胜负判断的顺序。

## 3. 实施步骤

### 1）配置、协议与模型边界

建议新增 `Match.PlayerCount`、`Match.ManualTickAdvance`，默认为 4 和 false；最终字段名可随实现保持简单一致。创建新局时读取并固定配置；人数非法拒绝创建，修改配置仅影响下一局。

协议涵盖登记、局部观察、查询、提交、淘汰及结束通知。查询／提交保留 gameId、roundId、requestId；玩家编号从连接绑定取得。UI 快照带配置人数、席位、推进模式、当前阶段、待开启轮及按钮可用状态；“tick演示”命令建议为 `tick.demonstrate`，关联 gameId、待开启 roundId 与 requestId。

### 2）核心适配实际人数与事件边界

排查核心循环、初始化、计划数量、出生映射、结果校验、观察、脚本加载和 UI 中固定四人的假设，全部改为按实际参赛人数处理；内部固定最大容量可以保留，但有效长度必须准确。未参赛席位不作为死亡玩家，也不进入计划等待集合。

保留现有四人脚本兼容与固定 initial 测试环境；正式对局按种子随机分配出生。提取可复用的计划几何校验，避免提交与执行使用两套规则。

将核心整轮 Advance 分解出开始及逐完整内部事件批次推进入口，原 Advance 可调用这些入口保持兼容。增加当前逻辑时刻掉线淘汰入口，复用淘汰、计划取消与胜负结算；模拟期间不得由网络线程直接修改世界。补齐第 500 tick 终点处理与不生成第 501 轮的约束。

### 3）登记、连接与串行协调器

实现独立 `/ws/ai`。登记数达到配置人数才就绪，额外登记明确拒绝，不设候补；准备断线后回到不足员状态并允许补位，开局后禁止补位。

协调器作为本局唯一状态修改者。建议阶段为 Preparing（含就绪状态）、AwaitingTick、Collecting、Simulating、Ended、Aborted。UI 开始和最后登记／掉线竞争通过串行处理裁决；每局只开启一次。

每个连接串行发送，接收解析后提交命令。等待网络发送不应阻塞本局处理其他请求或掉线；发送数据由发送任务明确持有至完成／失败／取消后归还。局末先固定结果、通知再关闭连接，下一局重新登记；清理不改判已结束结果。

### 4）冻结观察、查询与计划锁定

开启决策轮时依次激活增益、重置额度、捕获冻结状态、生成各玩家局部观察及目标表。免费观察提供自身完整状态；`participantIds` 仅列视野外其他玩家编号，视野内其他玩家放入 `visible.players` 并附位置，两者不重复且不含自身。补充自身在场泡泡数量与剩余行动值，付费详情保存在服务端，不随免费观察下发。

查询同一冻结状态：可见泡泡每次成功扣 1，视野内其他玩家扣 2，视野外其他玩家扣 3，额度每轮 10；失败不扣费。玩家查询统一返回唯一编号、位置、速度、泡泡容量上限、泡泡火力、视野宽度和在场泡泡数，视野外也返回位置；费用按本轮冻结可见性判定。同 requestId 查询重发成功仍收费。非法目标、错局／错轮、预算不足和锁定后查询返回明确原因。逐项协议确认见 [协议确认记录](对战协议_逐项确认.md)。

首次有效计划整份锁定、关闭查询；非法计划整份拒绝并允许修正；重发不覆盖或重复执行。合法方向上的实际阻挡和执行时容量不足由模拟处理，不在提交时泄露隐藏障碍。

等待期间掉线禁用该玩家查询目标，保留其他玩家原观察、预算和锁定计划；其已放泡泡仍按原轮编号与冻结详情可查。只收集存活参赛玩家的计划，在线迟交持续等待。

### 5）逐帧门槛、UI 与记录

自动模式开局与轮末直接开启下一轮；逐帧模式先进入 AwaitingTick，直到有效按钮命令才建立决策轮。完成一轮后丢弃本轮许可并再次等待，旧命令／旧定时唤醒不得越过门槛。

UI 展示实际人数与席位、就绪／等待按钮／等待哪些玩家／模拟／结束状态，开启开关时显示“tick演示”。玩家卡片和结果按实际人数展示，沿用全局动画，不用 UI 代替客户端输入。

新增连接、阶段转换、查询结果和费用、锁定／拒绝、掉线及终局日志，带 GameId、RoundId、逻辑时间、PlayerId、RequestId 等关联字段。每局 JSONL 保存配置、种子及实际出生、观察、每次请求与裁决、模拟事件和终止原因；写入失败停止进一步推进并保留现场，不重放查询恢复本局。

### 6）真实网络脚本客户端与核对工具

新增简单 C# 控制台客户端；验证运行器按配置启动 N 个客户端进程，每个按脚本执行有序请求并核对服务端响应。运行器可按预设屏障协调发送顺序、延迟、关闭连接及 UI 控制，以稳定复现目标场景，不能读取隐藏状态产生策略。

新验证脚本放 `scripts/battle/`，文档放 `docs/battle/`。脚本明确声明初始配置／种子、每轮请求、预期响应、观察字段、费用及余额、关键事件和最终现场。预期独立编写，不以同一模拟实现生成预期结果。

脚本没有提供存活玩家有效计划时，固定为“验证未完成”后清理连接，不通过清理掉线伪造胜负。用于观察等待行为的验证超时只是测试失败期限，不成为正式服务端动作超时规则。

## 4. 关键验收输入与预期

具体场景输入、扣费序列、正式地图九轮终局及运行步骤见 [对战流程验证方案](对战流程验证方案.md)。

| 验收输入 | 明确预期 |
| --- | --- |
| 分别配置 2、3、4 人；尝试少一人开局和多一人登记 | 不足人数不开始，人数齐仅就绪，UI 开始后才开局；额外登记拒绝，未参赛角无玩家／死亡事件 |
| 人数配置 1、5 或非整数 | 创建失败，返回具体原因，不静默改成四人 |
| 固定种子分别创建 2／3／4 人对局 | 出生互不重复且均为四角之一，同配置与种子实际分配一致；记录可核对 |
| 逐帧模式点击 UI 开始后保持不点“tick演示” | 不收到 round.started，不接受新轮查询／提交；逻辑时间仍为 0 |
| 逐帧模式点击一次、收齐计划并完成一轮，再保持不点击 | 只收到一轮观察，只模拟一轮；不提前激活下一轮增益／重置预算／下发下一轮观察，泡泡时间保持不变 |
| 同轮重复点击、并发 UI 点击，以及在下一轮重发旧点击命令 | 同一待开启轮只开启一次，不积攒许可、不越轮推进 |
| 自动模式按脚本提交多轮有效计划 | 无需 tick 点击，连续开启下一轮；仍遵守最小模拟开始间隔及全员有效计划条件 |
| 同一初始状态、种子和请求脚本，分别自动与逐帧运行 | 除现实等待与 UI 控制记录外，观察、扣费、事件逻辑时刻和最终状态一致 |
| 可见泡泡、视野内／外玩家查询、同 requestId 重发、余额耗尽、不可见泡泡／过期目标 | 泡泡成功扣 1；玩家视野内扣 2、视野外扣 3，并均返回七项详情含位置；失败不扣费，不返回详情 |
| 非法方向／越界或路径外放置后修正，再重复提交其他计划及查询 | 非法不锁定；首次有效锁定；后续不替换、不重复执行，锁定后查询拒绝 |
| N−1 人提交，最后一人暂不提交 | 时间、位置、泡泡剩余逻辑寿命不变；最后一份有效计划到达后只推进一轮 |
| 准备阶段掉线后补位；开局后等待按钮／决策时掉线 | 准备释放席位，不淘汰；开局后当前时刻淘汰、不补位，剩一人／零人无需点击立即结束，仍多人则保留当前阶段 |
| 等待决策时掉线，其他玩家已查询或锁定 | 原观察、余额和锁定不重置；禁用掉线玩家查询；其视野内遗留泡泡保持原轮查询语义 |
| 模拟期间掉线与爆炸在同一内部结算点 | 取消掉线者未执行计划，与同刻到期及连锁合并淘汰后统一判胜负，不提前判赢；必要时用核心确定性夹具补足网络脚本难以稳定注入的时序 |
| UI 断开与重连；正常终局清理 AI 连接后创建下一局 | UI 断开不淘汰；逐帧等待可重连继续，自动模式可持续运行；清理不改判，下一局无旧预算、计划或命令残留 |
| 500 tick 多人存活、途中胜负、脚本耗尽／断言失败 | 上限终点依规则结算，不进入 501；途中终局不补满；验证未完成与竞技结果分开 |

每个网络场景同时核对客户端收到的响应、服务端日志／记录和全局最终现场，浏览器核对实际人数、按钮阶段与最终状态。修改核心人数及事件入口后，运行现有四人精确时间、道具及必要 M0 场景回归；通过后仅因新变更或未解决风险追加验证。实际运行结果另见验收记录。

## 5. 工程约束

局部容器从对应池租用，冻结状态、锁定计划和待发送消息都明确唯一所有者及最后使用时机。异常、取消、终局和下一局重建可靠归还，池数组使用有效人数／有效长度，不把租用容量当人数。高频对象按需要复用；不引入通用池框架。

只为关键同刻结算、并发点击和生命周期风险添加最少必要检查，不建立形式化覆盖率目标。完成后默认保留工作区改动，不自动提交或推送。
