# ClientAI 第一版

实现位于 `src/QQT.ClientAI`，C#／.NET 10 本地搜索，无模型服务或额外训练依赖。参赛连接仅访问 `/ws/ai`，按每轮观察和合法付费查询决策，保留公开地图先验与历史记忆。四类道具各 8 个、共 32 个是本次对抗验证配置，服务端默认值未改。

## 启动

以下示例按仓库约定使用 `rtk`。当前执行环境未安装可调用的 rtk，本次实际验证使用了对应的原生命令。

```powershell
rtk dotnet build QQT.sln
rtk dotnet run --project src/QQT.ClientAI.Checks --no-build
rtk python scripts/verification/client-ai-battle.py --output artifacts/client-ai/new-run
```

第三条会启动一个独立 Server（默认 5091 端口）、四个独立 ClientAI 进程，配置正式地图和每种 8 个随机道具，经 UI 控制连接创建并开局，等待正常终局，核对预算、锁定、动作几何、进程退出码及四个客户端／Server／UI 结果一致。默认出生种子 1847，道具种子 7319，策略种子分别为 101、211、307、419。只有编排器掌握出生／道具种子，AI 仅得到 gameId 和自身策略种子。选择新输出目录，已有报告不会被覆盖。

Server 最小推进间隔在验证进程中设为 20ms，逻辑时间与规则不变。正常手动运行仍沿用服务端默认 1000ms。UI 连接在开局后退出、终局后重新连接取证，避免每轮重复传输全局历史；服务端全量事件仍持续落盘。

手动运行：

```powershell
rtk dotnet run --project src/QQT.Server -- --battle
```

打开 `http://127.0.0.1:5080` 创建四人对局，从创建结果取得 gameId。在四个终端分别启动下列客户端，使用不同 `--seed` 和独立 `--log` 路径，满员后在 UI 开局：

```powershell
rtk dotnet run --project src/QQT.ClientAI -- --server ws://127.0.0.1:5080/ws/ai --game-id <gameId> --seed 101 --log artifacts/client-ai/manual-p1.jsonl
```

`--server` 是完整 AI WebSocket 地址；AI 不负责创建和启动比赛。终局后退出，下一局重新传入 gameId 并登记，不支持同局重连。退出码 0 表示收到真实终局，胜负由 `match.ended.winnerId` 判断；1 为故障，2 为未收到终局即断开，130 为人工取消。

参数：`--nodes` 默认 60000，是额外候选的软逃生搜索节点预算，至少 1000；当前候选评估完成后再检查预算，五个基本方向始终评估。`--log-level`、`--transport-log-level`、`--search-log-level` 独立控制日志级别，默认 Information。完整消息和逐候选记录使用 Debug，查询目的、费用、余额和最终选择使用 Information。

## 决策职责

- `WorldMemory`：本局唯一记忆所有者。当前可见区域重新编号泡泡；视野外记录标记为估计。自身放置预测在计划锁定后记为未确认推测，下轮仍用观察／查询校准，不将提交等同于执行成功。
- `ClientSession`：独立接收任务向有界通道交接拥有自己解析存储的 JsonDocument；策略串行更新记忆。请求逐项关联，查询不盲目重发，提交核对返回的锁定计划；只在非法计划未锁定时修正一次空等待计划。
- `Forecast`：对每个候选按有理数推进跨线、回退、中心放置、到期及同刻连锁，所有射线共享该批旧地图。建立可共享的未来爆炸时间线，供逃生分支查询。当前轮拾取火力／移速在下一轮生效；未来未执行的属性拾取不拿固定旧属性证明退路安全。
- `Planner`：生成五个方向、不放泡、起点／沿途单点和少量两／三点组合。束宽 24，通常看 5 tick，按自身寿命调整至最多 16 tick。比较完整逃生、当前推进、毁箱增量、增益、访问循环、对手可达逃生位置和不确定性。接敌时优先推演最多四个威胁较大的对手起点／沿途放泡情景，包括途中释放容量；每轮重新规划。
- `AiLog`：Lifecycle／Transport／Query／Search／Decision 分类结构化 JSONL，关联 gameId、roundId、playerId、requestId 和精确逻辑时间。候选日志包含逃生深度、进攻值、风险与额外毁箱，决策日志保存实际搜索耗时。

局部容器、搜索前沿、地图、位图批次及消息缓冲均由数组池租用；小型状态用值类型。实例持有的池数组在 Dispose 归还，临时验证数组在 finally 归还；发送完成前不重置缓冲，排队文档不借用复用中的接收数组。框架通道、JSON 解析等内部仍可能分配，不声称零 GC。

## 验证与限制

预期见 [验证方案](ClientAI验证方案.md)，真实运行结果、证据和优先改进点见 [对抗复盘](ClientAI第一版_对抗复盘.md)。

第一版是有限观察与有限情景下的搜索算法。不会读取隐藏箱内道具、UI 帧或其他客户端日志来决策；估计过的“安全”不能覆盖尚未观测的泡泡。未对所有玩家的所有同时放置组合做穷举；未来逃生分支只移动，不继续放泡，敌方范围未来增益也无法完整预测。对未知泡泡暂用风险估计，尚未建立到期区间和概率信念。当前查询按威胁／接敌／定位价值排序，尚未计算查询前后行动排序的严格信息价值。

未修改玩法或服务端协议。验证中的相同种子复测只说明该场景可复现，不等于获得跨地图／对手的胜率证明。
