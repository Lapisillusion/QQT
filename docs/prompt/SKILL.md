# QQT 智能决策客户端生成

## 目标

编写一个可实际连接 QQT Server 的智能决策 AI：根据每个 tick 提供的观察，合理分配行动值，查询对当前决策有高回报的信息，作出有利于获得游戏胜利的移动和泡泡放置决策。策略必须随实际观察和查询结果变化，不能用预定动作序列冒充 AI。

本 skill 指导生成客户端；技术栈和代码位置遵循使用者要求及仓库约定。保持服务端现有玩法与协议，发现影响接入或决策的文档／实现矛盾时，指出具体冲突并与使用者讨论。

## 游戏简介与获胜方式

QQT 是用于 AI 比拼的简化泡泡堂游戏。每局 2／3／4 人自由混战，从 21×21 地图四角随机分配互不重复的出生点。玩家沿四方向移动，放置定时泡泡摧毁箱子、打开通道、获取增益并攻击对手；墙不可破坏，玩家互不阻挡、可以同格。

爆炸命中即淘汰，没有救援或复活。每批同刻到期与连锁、掉线与受击淘汰全部结算后，最后一名存活者立即获胜，全部淘汰为平局。结算可能在 tick 途中结束，结束后不再继续模拟未来泡泡。模拟上限默认 500 tick，可配置，以登记返回的 rules.maxTicks 为准；终点结算后仍有多名存活者则判平，不按毁箱数或道具数判胜。以 `match.ended` 为最终结果，不能把脚本完成、主动退出或连接关闭当作获胜。

默认初始属性为速度 1 格/tick、泡泡容量 3、每方向火力 1 格、泡泡寿命 3 tick、视野半径 2、每轮行动值 10。移动速度、容量、火力和视野可通过道具增加；不要将初始值硬编码为整局不变，以本轮 `self` 和合法查询为依据。坐标为整数 `{x,y}`，各取 0～20，x 向右、y 向下。

## Server 运行特性与每 tick 交互

Server 是权威模拟器，每进程同时运行一局。AI 参赛使用 `ws://127.0.0.1:5080/ws/ai`，地址应可配置。`/ws/ui` 是独立观战／控制通道。由启动参数或外部对局控制者提供当前 `gameId`；不要依赖从 UI 全局状态或服务端记录获取战场信息来决策。

每个 AI 使用独立参赛连接：

1. 准备阶段发送 `register.request`，从 `register.result` 获得绑定的 `playerId`、本局人数和 `rules`（tick上限、额度、三类费用）。身份由连接决定，不能替其他玩家行动。达到配置人数后，仍由 UI 手动开始。
2. 等待 `round.started`。第一轮 `roundId=1`，其起始逻辑时间为 0；不要将轮编号直接当作观察时间。自动模式由 Server 开启下一轮；逐帧模式首轮和后续各轮都等待 UI 点击“tick演示”，此后才下发观察。AI 不发送 UI 控制命令，也不以现实计时自行开启下一轮。
3. 接收 `time, self, participantIds, visible`，获取本轮观察与预算。各玩家的观察及付费详情来自同一逻辑时刻的冻结状态。
4. 在计划未锁定时，用 `query.request` 逐项查询，处理 `query.result`，根据新增信息调整候选策略。查询期间逻辑世界冻结；查询不会让泡泡走时。
5. 发送 `action.submit`，检查 `action.result`。首次合法计划锁定后，不再查询或修改本轮计划。非法提交未锁定时可以修正；重复提交返回原锁定计划，不替换或重复执行。
6. Server 收齐所有存活玩家的合法计划后模拟最多一个 tick。途中没有新的观察或改向机会；可能先收到淘汰或结束通知。对局继续才等待下一次 `round.started`，不要在本地擅自递增轮次并发送请求。

未提交时整局继续等待，没有迟交后自动代走或淘汰的规则；现实等待不增加逻辑时间、泡泡计时或 tick 上限。默认相邻模拟开始至少间隔 1 秒，可配置，和 UI 动画时长相互独立。客户端应可靠地产生决策，不能依赖服务器超时补动作。

准备阶段掉线释放席位、允许补位；开局后在等待按钮、查询决策、模拟等任何阶段掉线均淘汰，不支持本局重连恢复。淘汰者已有泡泡保留；等待阶段他人掉线不刷新自己的观察、预算或锁定计划，目标玩家查询会被禁用。正确处理 `participant.eliminated`，结束后关闭本局资源，下一局重新连接登记。

### 交互字段与信息边界

- 查询和决策请求携带准确的 `type, gameId, roundId, requestId, payload`，`requestId` 为字符串，仅关联响应；登记不要求 `roundId`，主动通知不带 `requestId`。按协议处理各自 result 及通用 `error`，根据 `error.code` 分支。
- `self` 免费提供自身状态；`visible.players` 仅免费提供视野内其他玩家编号和位置；`participantIds` 仅列视野外其他存活玩家编号，两者都排除自身且不重复。
- `visible.cells/bubbles/items` 只描述本轮视野内的地形、泡泡和露出道具。未出现的视野外格子不代表空地，箱内道具不公开。方形视野受地图边缘裁剪，墙和箱子不遮挡视野。
- 泡泡的 `queryId` 只在本轮有效，下轮重新分配；同格多颗各有编号。玩家 `playerId` 在本局跨轮稳定。禁止把泡泡查询编号当作跨轮实体 ID。
- `action.submit.payload` 必须有 `direction`（`wait/up/down/left/right`）和 `placements`（坐标列表，无泡泡时为 `[]`）。距离由本轮速度决定，不能自填距离或中途改向；放置坐标必须位于起点及名义直线路径，等待只能在当前格放置，同轮同中心不能重复请求。
- 接受计划不代表执行成功：实际阻挡、容量不足、未到达中心、淘汰和提前终局都可能阻止动作，不能把提交成功等同于放置成功。

## 必须正确建模的精确时间

逻辑时间是精确分数 tick，协议编码为 `{numerator,denominator}`。用有理数或等价的精确比较表示，不用浮点近似或现实秒数裁决同刻，也不将所有事件取整到 tick 边界。

- 每颗泡泡按实际放置时刻 `p` 独立计时，预定到期 `dueAt=p+L`。例如速度 3、t=0 出发，t=1/3 到相邻格中心放置，寿命 3，则到期为 t=10/3。计划在终点放置与起点放置的到期时间不同。
- `dueAt` 是预定到期，连锁可能提前引爆。同格及邻近泡泡要共同纳入威胁推演；不能只逐颗检查各自到期。
- 玩家从中心在时刻 s 以速度 v 出发，相邻格跨线检查在 `s+1/(2v)`，到下一中心在 `s+1/v`。成功跨线当刻归新格，放置仍需到中心；跨线失败则仍归旧格，以原速度退回刚离开的中心并结束剩余移动，不因障碍随后消失自动重启。
- 墙、箱子、泡泡阻挡进入，玩家不阻挡。泡泡生成时已在该格的玩家有针对该颗泡泡的离开许可，离开后不能凭该许可再次进入。
- 同刻顺序为：推进位置并按处理前障碍判跨线 → 处理待结算掉线 → 以同一份旧地图计算全部到期和连锁 → 统一移除与淘汰 → 检查胜负 → 存活者中心拾取 → 放置 → 后续移动。恰好同刻爆掉的泡泡仍阻挡本次跨线，同刻炸掉的箱子仍阻挡本批其他爆炸射线。
- 爆炸覆盖中心及四方向；硬墙不被覆盖且截断，箱子被覆盖销毁并截断，泡泡被覆盖触发连锁但不截断原射线。爆炸伤害瞬时发生，只看该时刻的归属格，没有持续火焰伤害。
- 拾取的道具下一轮生效；火力增益会影响此前已放置泡泡在后续轮次的爆炸范围。查询的 `blastRange` 是当前轮生效范围，不能永久固定为放置时或首次查询时的范围。

候选行动的安全检查必须覆盖整个 tick 的时空路径及后续逃生，不只比较终点是否处于当前十字范围。对不确定的敌方属性、视野外泡泡及未来连锁保留风险，避免用无法确认的假设证明安全。

## 查询预算与信息价值

每轮行动值按本局 rules.actionPoints 重置，默认 10，未用余额不累积，仅用于查询，移动和放置不耗行动值。费用与返回字段严格按协议：

| 查询目标 | 默认成功费用 | 返回详情 |
| --- | --- | --- |
| 本轮可见泡泡，包括自己的 | 1 | `ownerId, blastRange, dueAt` |
| 视野内其他玩家 | 2 | `playerId, position, speed, bubbleCapacity, blastRange, visionWidth, activeBubbleCount` |
| 视野外其他玩家 | 3 | 与视野内相同，包含位置 |

玩家详情的 `visionWidth` 是未裁剪边长 `2R+1`，不要与 `self.visionRadius` 混用。泡泡不能查询视野外目标，玩家查询不提供其逐颗泡泡位置。

成功重复查询（包括重用相同 requestId）仍扣费，失败不扣费且无详情。以 `query.result.actionPoints` 校准预算，不盲目重发查询；首次合法提交后查询关闭。优先在收到必要回复后再锁定动作。

为信息选择建立与决策相关的价值判断：先评估某项查询能否改变避险、逃生、拦截或进攻方案，再结合费用和已获得的信息排序。例如优先确认威胁当前路径的泡泡到期与归属；接敌时确认对手速度、火力及容量；需要搜索或追击时付费定位视野外玩家。避免机械查遍所有对象或为耗尽预算而查询，低价值信息可以不买。

AI 决策的信息来源限于参赛观察、合法查询和公开规则，不读取 UI 全局帧、其他客户端记录或服务端隐藏现场。

## 实现与交付要求

将协议收发与轮次状态、查询选择、精确威胁推演及动作选择组织成可理解的职责，避免策略计算阻塞消息接收。记录关联 gameId／roundId／requestId 的查询目的、余额、风险依据及计划，便于解释决策。

策略应兼顾存活、通道扩展、增益获取、对手位置与逃生路线压缩。放置泡泡前评估自身退路及可能连锁；考虑本局 tick 上限的平局条件，以最终获胜为目标权衡风险。没有明确安全行动时选择风险较小的合法方案，不无限查询或停留在未提交状态。

交付可运行的客户端及其启动命令，说明 Server 地址和 gameId 如何传入、如何启动多个独立实例及策略限制。可参考 `src/QQT.ScriptClient/Program.cs` 的传输行为与 `scripts/verification/battle.py` 的协议交互；其固定脚本、UI 断言和全局证据不能进入 AI 策略。

先给关键验证写清输入与预期，再验证实际协议接入、预算／锁定和精确时序避险等能区分重要错误的路径。使用固定种子复现问题，但不把固定出生点或对手动作编码成策略。仅报告实际运行结果；协议通过、单局偶然获胜和策略效果是不同证据，不将有限验证宣称为必胜。
