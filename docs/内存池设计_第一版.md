# 内存池设计：第一版

用户约定：局部容器必须通过池申请，禁止在业务代码中直接 new；高频对象尽可能池化。持续规范见 [AGENTS.md](../AGENTS.md)。M0 已实现数组池及 JSON writer／消息缓冲对象池；未使用的集合类型池按后续实际需要添加，不提前建立通用池框架。

## 1. 采用的能力

| 对象 | 方案 | 用途 |
| --- | --- | --- |
| 数组、字节缓冲区 | `System.Buffers.ArrayPool<T>` | 格子临时列表、事件缓冲、序列化与网络消息缓冲 |
| List、Dictionary、HashSet 等 | `Microsoft.Extensions.ObjectPool` 加项目容器重置策略 | 复用集合对象及其合理容量，不每次重新创建 |
| 高频可变引用对象 | 同一对象池机制，加类型专属重置策略 | 必要的执行上下文、可复用消息构建对象等 |
| 小型值对象 | struct／readonly struct，批量数据放在池化容器中 | 格子位置、移动段、简单事件；不为了池化额外制造引用对象 |

ArrayPool 用于数组租用与归还；ObjectPool 用于对象复用，池的保留数量不等于对象总分配上限。池未命中与集合扩容仍可能分配，因此不承诺零 GC。依据：[ArrayPool 官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.arraypool-1?view=net-10.0)、[ObjectPool 官方说明](https://learn.microsoft.com/en-us/aspnet/core/performance/objectpool?view=aspnetcore-10.0)。

不另引入第三方通用池库。项目只封装实际需要的容器类型、清理策略和所有权交接。

## 2. 租用与归还

业务代码遵循“租用 → 使用 → 可靠归还”，不得直接创建局部容器，也不通过 ToList、ToArray 或集合表达式间接创建。

- 池按类型集中建立并复用，不在每个 tick 或业务方法中创建新的池。
- 集合租用时为空；归还时 Clear 并重置业务状态。Dictionary／HashSet 的比较器是池的固定约定，不混用不同比较器。
- 容量按实际用途预估；大容量实例可以被归还策略拒绝保留，避免一次异常膨胀永久占用内存。
- 数组只使用有效区间；返回的长度可能大于请求值，内容也不能假定为零。
- 同一实例只有一个所有者。不可让两个代码路径分别归还同一容器，也不以可随意复制的租用句柄造成重复归还。
- 池本身支持并发操作，不代表取出的 List 等对象支持并发读写；仍遵守同局串行状态修改原则。

容器实际创建放在池工厂中。禁止局部业务 new 不禁止池为了首次提供对象而创建实例，也不等于禁止位置等 struct 的正常构造。

## 3. 同步与异步的生命周期

| 数据 | 所有者 | 归还点 |
| --- | --- | --- |
| 爆炸覆盖、待销毁箱子等临时集合 | 当前模拟调用 | 计算和读取完成后的 finally |
| 本 tick 的事件集合 | 模拟调用，或显式交接给协调器 | 日志、投影及其他使用者完成后 |
| 待发送字节缓冲 | 对应发送任务／队列 | 发送完成、失败或取消后，释放所有引用再归还 |
| 冻结观察或历史快照 | 决策轮／历史状态持有者 | 快照不再被查询、发送或回放使用时 |

不能“发送入队后立即归还”，也不能先归还事件容器再交给 UI 投影。若保留数据超出当前调用，必须转移所有权或复制到另一个有明确生命周期的自有缓冲区；复制所需容器仍从池申请。

多个发送任务共享同一缓冲时，必须等所有使用者完成；M0 优先使用简单的单所有者消息缓冲，避免过早引入引用计数框架。所有权原则参见 [Memory 与 Span 官方指南](https://learn.microsoft.com/en-us/dotnet/standard/memory-and-spans/memory-t-usage-guidelines)。

## 4. M0 的落地点

M0 从一开始执行强制池化约束，但只建立所需的少量池：

- 爆炸覆盖和箱子销毁临时结果采用池化数组／容器。
- 每轮事件使用池化缓冲，事件本身优先为简单值对象。
- UI 消息序列化和 WebSocket 发送缓冲明确由发送流程归还。
- 地图、脚本和四名玩家状态按场景生命周期持有，重新运行时正确释放旧场景资源；不每帧或每轮重建整个世界。
- 内存日志等跨 tick 数据持有独立所有权，不引用已归还的临时事件集合。

随着实现检查分配热点，再将其他高频引用对象纳入对应池。测量用于选择容量、保留策略和高频对象池化方式，不作为绕过局部容器强制池化的理由。

## 5. 验证要点

代码审查检查局部容器直接或隐式创建、遗漏归还和异步逃逸。实现后关注关键生命周期：异常与取消能归还，重复运行不读到旧数据，提前返回不遗漏资源，发送完成前不复用缓冲，清理后的容器不保留上一局引用。优先通过实际运行与必要诊断检查，不为每个池方法编写低价值用例；仅有明确风险或实际故障时补最少的关键回归验证。性能检查区分首次租用／扩容与热身后复用，不把功能正常当作零分配证据。
